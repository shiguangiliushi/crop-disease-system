# 生产部署样板（Linux 单机：Nginx + Gunicorn + systemd）

> **这份文档解决什么**：仓库里已有环境变量清单（`backend/.env.example`）、日志/备份/健康检查的
> 管理命令、定时任务脚本（`deploy/schedule/`），但**没有可照抄的 Nginx 与服务进程配置** ——
> 上线时全靠临时查资料，每人配出来的都不一样，出问题也不知道该对齐哪一份。
> 这里把三块拼成一条按顺序执行的上线路径，并把**本项目特有的坑**单独列出来。
>
> **不是**：Docker 部署（见 `docker-compose.yml` 与 [部署与运维.md](部署与运维.md) 的方式 B）、
> Kubernetes、多机负载均衡、CI/CD。
>
> 约定：项目根一律 `/srv/crop-disease-system`，示例域名 `example.com`。
> 文中带 `example.com`、`<...>`、`crop` 的地方都是**占位符**，照抄前逐个替换。

## 0. 三份样板文件

| 文件 | 复制到 | 作用 |
|---|---|---|
| [`deploy/nginx/crop-disease.conf.example`](../deploy/nginx/crop-disease.conf.example) | `/etc/nginx/conf.d/crop-disease.conf` | 前端 dist + SPA 回退、`/api/` 反代、**SSE 关缓冲**、media/static 分流、HTTPS 骨架 |
| [`deploy/systemd/crop-disease.service.example`](../deploy/systemd/crop-disease.service.example) | `/etc/systemd/system/crop-disease.service` | gunicorn 守护、开机自启、日志进 journald |
| [`backend/.env.example`](../backend/.env.example) | `/srv/crop-disease-system/backend/.env` | 全部环境变量（已有文件，本文只讲生产必填项） |

部署完成后目录长这样：

```text
/srv/crop-disease-system/
├── backend/                 # Django（manage.py 在这一层）
│   ├── .env                 # 600，含密钥；systemd 的 EnvironmentFile 指向它
│   ├── media/               # 用户上传 —— 要备份
│   ├── staticfiles/         # collectstatic 产物 —— 随时可重建
│   └── db.sqlite3           # 不用 PostgreSQL 时才有
├── frontend/dist/           # 前端产物 —— 仓库里没有（dist/ 被 .gitignore 忽略），必须自己构建
├── deploy/                  # 本文配套的 .example 配置 + schedule/ 定时任务
└── venv/                    # Python 虚拟环境
```

## 1. 流程清单（一页照做）

### 1) 装系统依赖

```bash
sudo apt update
sudo apt install -y python3 python3-venv python3-pip nginx git \
                    libglib2.0-0 libgl1 libsm6 libxext6 libxrender1
# 上面那几个 lib* 是 OpenCV 的依赖（和 backend/Dockerfile 里装的是同一组），
# 缺了会在 import cv2 时报 "libGL.so.1: cannot open shared object file"。

# 强烈建议：共享缓存。多 worker 下限流计数要跨进程共享，否则限额被放大 N 倍（见 2.7）
sudo apt install -y redis-server

# 可选：PostgreSQL（不装就用 sqlite —— 单机小流量可以，但并发写会锁库）
# sudo apt install -y postgresql
```

Python 要 **3.10+**（Django 5.2 的要求；Debian 12 自带 3.11、Ubuntu 24.04 自带 3.12 都行）。

```bash
sudo mkdir -p /srv && sudo chown "$USER" /srv
git clone <仓库地址> /srv/crop-disease-system
cd /srv/crop-disease-system
python3 -m venv venv
./venv/bin/pip install --upgrade pip
./venv/bin/pip install -r backend/requirements.txt -r backend/requirements-prod.txt
```

> `requirements.txt` 里有 torch（CPU 轮子约几百 MB），首次安装慢且吃磁盘，先 `df -h` 看一眼。
> `requirements-prod.txt` 里是 gunicorn / whitenoise / redis 这类**部署件**（不装也能跑，但生产要装）。

### 2) 建 `.env`

```bash
cd /srv/crop-disease-system/backend
cp .env.example .env
chmod 600 .env
# 生成 SECRET_KEY（用 venv 里的 python，确保能 import Django）
/srv/crop-disease-system/venv/bin/python -c \
  "from django.core.management.utils import get_random_secret_key as g; print(g())"
```

生产**必须**改的（其余按需，逐项说明见括号里的章节）：

```ini
# —— 安全（必改，不改会拒绝启动，见 2.1）——
DJANGO_DEBUG=False
DJANGO_SECRET_KEY=<上一步生成的串>
DJANGO_ALLOWED_HOSTS=example.com,www.example.com

# —— 强烈建议：限流正确性 / 备份 / 邮件链接（见 2.7、备份与恢复.md）——
DJANGO_CACHE_URL=redis://127.0.0.1:6379/1
DJANGO_BACKUP_DIR=/data/backups
FRONTEND_BASE_URL=https://example.com
DJANGO_EMAIL_BACKEND=django.core.mail.backends.smtp.EmailBackend

# —— 按部署形态决定（见 2.3）——
DJANGO_SERVE_MEDIA=False
DATABASE_URL=postgres://crop:***@127.0.0.1:5432/crop_disease

# —— 助手（见 2.2）——
LLM_API_KEY=<真实 key>
LLM_TIMEOUT=30
LLM_MAX_TOKENS=2000
```

> `DJANGO_BACKUP_DIR` 要指到**另一块盘**或网络存储（和数据库同盘的备份遇到磁盘故障会一起没）。
> `DATABASE_URL` 留空就用 sqlite；用 PostgreSQL 时记得先装驱动（`psycopg[binary]`，见 `requirements-prod.txt` 注释）。

> ⚠️ `.env` **不支持行尾注释**：`settings.py` 的 `_load_env_file` 只把**行首**的 `#` 当注释，
> 行尾的 `# ...` 会被原样算进值里。例如 `LLM_MAX_TOKENS=2000   # 说明` 会让值变成
> `2000   # 说明`，`int()` 直接抛 `ValueError`，服务起不来（systemd 的 EnvironmentFile 也是同样的规则）。
> 注释请**另起一行**，像上面那样。
>
> ⚠️ `.env.example` 里的 `DJANGO_ALLOWED_HOSTS=*` 是**开发默认值**，不改的话服务会直接拒绝启动（2.1）。
> ⚠️ 改完 `.env` 必须 `sudo systemctl restart crop-disease`：settings 只在进程启动时读一次。

### 3) 迁移数据库

```bash
cd /srv/crop-disease-system/backend
/srv/crop-disease-system/venv/bin/python manage.py migrate --noinput
# 注意顺序：check_env 也会检查"迁移是否都应用了"，全新库上先跑它必然退出码 1
/srv/crop-disease-system/venv/bin/python manage.py check_env --strict   # 环境自检，有问题退出码非 0
/srv/crop-disease-system/venv/bin/python manage.py check                # 顺带验证生产守卫能过
```

`check_env` 会对照 requirements 检查版本、数据库连通、缓存、迁移状态和模型文件；
`manage.py check` 与 gunicorn 启动走**同一段** settings 加载逻辑，所以它是"服务能不能起来"的
最便宜预演（见 2.1）。

### 4) 收集静态文件

```bash
cd /srv/crop-disease-system/backend
/srv/crop-disease-system/venv/bin/python manage.py collectstatic --noinput
test -f staticfiles/admin/css/base.css && echo "collectstatic OK"
```

不跑这一步的后果：admin 页面 HTML 在、CSS/JS 全 404 —— 页面看起来像坏了，实际只是没收集静态文件。

### 5) 起 systemd 服务

```bash
sudo useradd --system --home /srv/crop-disease-system --shell /usr/sbin/nologin crop
# 让运行用户可以写 media / sqlite（用 PostgreSQL 时只需要 media）
sudo chown -R crop:crop /srv/crop-disease-system/backend/media
sudo chown crop:crop /srv/crop-disease-system/backend/db.sqlite3 2>/dev/null || true
# 密钥文件：root 拥有、服务用户可读
sudo chown root:crop /srv/crop-disease-system/backend/.env && sudo chmod 640 /srv/crop-disease-system/backend/.env

sudo cp deploy/systemd/crop-disease.service.example /etc/systemd/system/crop-disease.service
sudoedit /etc/systemd/system/crop-disease.service        # 改 User/Group/路径（文件里已标注）
sudo systemctl daemon-reload
sudo systemctl enable --now crop-disease
systemctl status crop-disease --no-pager
journalctl -u crop-disease -n 50 --no-pager
curl -fsS http://127.0.0.1:8000/api/health/
```

`curl` 能通就说明"Django + gunicorn + 数据库"这一层已经活；Nginx 还没上，这是好事 ——
分两层排查比一起上快得多。

### 6) 构建前端（**先设 API 地址**）

```bash
cd /srv/crop-disease-system/frontend
VITE_API_BASE_URL=/api npm ci
VITE_API_BASE_URL=/api npm run build-only
ls dist/index.html
# 关键检查：产物里不该再出现开发机地址
grep -rl "127.0.0.1:8000" dist/assets/ && echo "⚠️ 还带着开发地址，别上线！" || echo "OK"
```

为什么必须传这个变量：`frontend/src/api/assistant.js` 里写的是
`import.meta.env.VITE_API_BASE_URL || 'http://127.0.0.1:8000/api'` —— Vite 在**构建时**把值替换成字面量。
不传的话，部署后每个用户的浏览器都会去连**他自己电脑**的 8000 端口：页面能打开，但登录、识别、助手全部失败。
（详见 2.8。Node 需 20.19+ 或 22.12+（Vite 7 的要求），`node -v` 先确认。）

### 7) 配 Nginx（先只上 80 端口）

```bash
sudo mkdir -p /var/www/certbot
sudo cp deploy/nginx/crop-disease.conf.example /etc/nginx/conf.d/crop-disease.conf
sudoedit /etc/nginx/conf.d/crop-disease.conf
#   ① 把 server_name 改成真实域名
#   ② 证书路径先别管 —— 但要把整个 443 server 块**注释掉**，否则证书文件不存在会让 nginx 起不来
#      （原因与顺序见 .example 文件末尾"证书还没申请时"那段）
sudo rm -f /etc/nginx/sites-enabled/default      # Debian/Ubuntu：默认站点会抢 80 端口
sudo nginx -t && sudo systemctl reload nginx
curl -I -H 'Host: example.com' http://127.0.0.1/   # 期望 301 到 https（说明 80 段已生效）
```

### 8) 申请证书

```bash
sudo apt install -y certbot
sudo certbot certonly --webroot -w /var/www/certbot -d example.com -d www.example.com
sudo certbot renew --dry-run
systemctl list-timers | grep certbot      # certbot 自带续期 timer
```

用 `certonly --webroot` 而不是 `--nginx`：`--nginx` 会自动改配置，和本样例的 443 段容易打架；
`--webroot` 只写证书，配置完全由你掌控（样例的 80 段已经留好 `acme-challenge` 路径）。

### 9) 打开 HTTPS 并回归

```bash
sudoedit /etc/nginx/conf.d/crop-disease.conf     # 取消 443 注释、证书路径改成实际域名
sudo nginx -t && sudo systemctl reload nginx
```

```bash
curl -fsS https://example.com/api/health/                     # 后端经 Nginx 可达
curl -I  https://example.com/                                 # 200 + index.html
curl -I  https://example.com/detection/history                # 200 + index.html（SPA 回退生效）
curl -I  https://example.com/static/admin/css/base.css        # 200（collectstatic 已跑）
curl -I  https://example.com/admin/                           # 302 到登录页（不是前端 200）
```

助手是流式的，单独验一次（把 `<token>` 换成真实登录 token）：

```bash
curl -N -X POST https://example.com/api/assistant/ask/stream/ \
     -H 'Authorization: Token <token>' -H 'Content-Type: application/json' \
     -d '{"question":"番茄叶霉病怎么防治"}'
```

期望：文字**一块一块**冒出来。如果先静默几秒、然后整段一次性出现，就是 SSE 被缓冲了（2.4）。

HTTPS 稳定运行几天后再开 HSTS：`.env` 加 `DJANGO_SECURE_HSTS_SECONDS=31536000` 并重启。
**不要**一上线就开 —— 浏览器会记住这个域名只走 https，回退很麻烦（`settings.py` 里默认就是 0）。

### 10) 装定时任务（指向已有的 `deploy/schedule/`）

```bash
sudo mkdir -p /var/log/crop-disease && sudo chown crop:crop /var/log/crop-disease
sudo crontab -u crop -e        # 以运行服务的同一个用户装，避免权限/路径不一致
# 粘贴 deploy/schedule/crontab.example，改三处：
#   PY=/srv/crop-disease-system/venv/bin/python
#   APP=/srv/crop-disease-system/backend
#   LOG=/var/log/crop-disease
sudo crontab -u crop -l
```

五件事（`crontab.example` 里的时间）：

| 任务 | 频率 | 不挂的后果 |
|---|---|---|
| `backend_backup` | 每日 02:30 | 出事时没有可恢复的数据 |
| `backup_verify` | 每日 03:10 | 备份坏了也不知道（"备份没验证过 = 没备份"） |
| `health_snapshot` | 每日 03:40 | 管理端「14 天趋势」少一格，页面照常打开、没人会发现 |
| 清理孤儿图片（`prune_media`） | 每日 04:10 | media 只增不减 |
| 注销冷静期到期（`purge_deletion_requests`） | 每小时 :05 | 用户以为账号已注销，个人信息还在库里 |

> ⚠️ **粘贴前先核对命令名**：`crontab.example` 与 `deploy/schedule/README.md` 里写的是
> `cleanup_media` 和 `process_deletions`，但当前代码里**没有这两个命令**
> （`backend/api/management/commands/` 下实际是 `prune_media` 和 `purge_deletion_requests`）。
> 照抄这两行，cron 只会在日志里留下 `Unknown command`，而且**不会有人收到通知**。
> 本仓库不改 `deploy/schedule/`（超出本次范围），部署时请把这两行替换成：
>
> ```cron
> 10 4 * * * cd $APP && $PY manage.py prune_media --yes --min-age-days 7 >> $LOG/media.log 2>&1
> 5 * * * *  cd $APP && $PY manage.py purge_deletion_requests >> $LOG/deletions.log 2>&1
> ```
>
> 另外：`docs/部署与运维.md` 里那段 cron 写的是 03:00/03:30/04:00/04:00/04:30，与
> `crontab.example` 的 02:30/03:10/03:40/04:10/:05 不一致 —— 以你实际粘贴的那份为准，别混用。
> 还要记住：**cron 用的是服务器本地时区**，`timedatectl` 确认是 `Asia/Shanghai`，否则 02:30 不是你以为的 02:30。

装完手动试跑一条，确认权限和路径都对：

```bash
sudo -u crop bash -lc 'cd /srv/crop-disease-system/backend && /srv/crop-disease-system/venv/bin/python manage.py backup_verify --strict'
```

> `crontab.example` 把输出重定向到 `$LOG/*.log`，这些文件**没有轮转**，会长大。
> 要么配 logrotate，要么接受它（比起"任务没跑"，日志变大是小事）。

## 2. 本项目特有的坑

每条都标了**症状 → 原因 → 怎么查/怎么修**。代码位置按本次核对时的行号写，改动后以搜索为准。

### 2.1 `DJANGO_DEBUG=False` 时有两道启动守卫，会**直接拒绝启动**

- **症状**：`systemctl start crop-disease` 立刻失败，`systemctl status` 只有
  `status=1/FAILURE`；真正原因在 `journalctl -u crop-disease` 里：
  `django.core.exceptions.ImproperlyConfigured: 生产模式（DJANGO_DEBUG=False）必须设置 DJANGO_SECRET_KEY…`
  或 `生产环境配置不安全，已拒绝启动：· DJANGO_ALLOWED_HOSTS 仍包含 "*"…`。
- **原因**：`backend/crop_disease_backend/settings.py` 里有**两处**检查，作用时机不同：
  1. 第 110–118 行（早于一切）：`DEBUG=False` 且 `SECRET_KEY` 还是占位值
     `django-insecure-!your_secret_key_here!` → 立即 `raise`。**注意：这一处不受
     `DJANGO_ALLOW_INSECURE` 豁免**。
  2. 第 1004–1022 行（文件末尾）：`DEBUG=False` 时再查 `SECRET_KEY == 占位值` 与
     `ALLOWED_HOSTS` 含 `*`；命中就拒绝启动。这一处可以用 `DJANGO_ALLOW_INSECURE=1` 显式跳过
     （内网演示用，**公网不要**）。
     （注：密钥还是占位值时第 1 处就先抛了，所以末尾这条的 `SECRET_KEY` 分支实际走不到；
     真正日常会撞上的是它的 `ALLOWED_HOSTS` 分支 —— 也就是 `.env` 里那行 `*`。）
- **怎么修**：填真实的 `DJANGO_SECRET_KEY`（生成命令见流程第 2 步）与真实域名。
- **怎么提前发现**：守卫在 **import settings 时**执行，所以 `manage.py` 的任何子命令都会触发它。
  在敲 `systemctl start` 之前先跑：
  ```bash
  cd /srv/crop-disease-system/backend && /srv/crop-disease-system/venv/bin/python manage.py check
  ```
  这一条过了，gunicorn 启动时就不会卡在同一处。
- ⚠️ 这**不是**"改完 .env 就热生效"的配置：必须重启服务（`systemctl restart crop-disease`）。

### 2.2 `LLM_MAX_TOKENS` 建议 2000（默认值），别往小调

- `settings.py:922` 的默认值是 **2000**；`backend/.env.example` 里示例写的是 **2500**
  （第 209 批为了"某作物的**所有**病害"这类清单题提高了上限）。
- 调小的后果不是报错，而是**回答被截在半句话**：第 204 批实测 800 时，
  "苹果跟葡萄"这种跨两个词条的问题答 1400+ 字，直接被截断（`finish_reason='length'`）。
  截断时库里 `AssistantMessage.truncated=True`，界面会提示"回答可能不完整"。
- 建议值：**2000**（默认）到 2500 都行；**不要低于 2000**。这个值不影响内存，只影响 token 账单。
- 怎么查实际生效值：
  ```bash
  /srv/crop-disease-system/venv/bin/python manage.py check_assistant
  # 会打印 LLM_ENABLED / 模型 / 超时 / 上限 tokens
  ```

### 2.3 `DJANGO_SERVE_MEDIA`：有 Nginx 时应当**关掉**

- `settings.py:279`：`SERVE_MEDIA = _env_bool('DJANGO_SERVE_MEDIA', DEBUG)` —— 生产默认 `False`。
- `backend/crop_disease_backend/urls.py:516`：只有它为 `True` 时才挂 `/media/` 路由。
- 有 Nginx 时保持 `False`：公开目录由 Nginx 直发（快、省一个 Python 进程），
  私有目录在 Nginx 里被单独正则拦下、回源给 Django 鉴权 —— 两件事互不依赖。
- 设成 `True` 的后果：多一条 Django 路由，请求已经被 Nginx 接走，属于"配了也不生效"的开关；
  唯一真正有用的场景是**单机/内网演示、根本没装 Nginx**。
- 反过来，设 `False` 但 Nginx **没配** `/media/` → 所有图片 404（"图片全碎了"）。
  这条与 2.4 是部署后最容易被当成"代码 bug"的两个现象。

### 2.4 SSE 被缓冲 → 助手"回答一次性蹦出来"

- **症状**：提问后转圈很久，然后整段答案瞬间出现；后端日志里生成明明是逐步的。
- **原因链**：
  - Nginx 默认 `proxy_buffering on`，把上游 SSE 帧攒在缓冲区里（普通 JSON 是优化，对流式是灾难）；
  - Django 侧其实已经做了两件事：`api/views_assistant.py:225` 用 `StreamingHttpResponse`，
  `:227` 发 `Content-Encoding: identity`（绕开 GZipMiddleware），`:229` 发 `X-Accel-Buffering: no`；
  - 但"响应头不被透传"的情况很常见（中间再加一层网关/云 LB、或有人改了视图），所以
    **Nginx 侧显式关缓冲**才是稳的（样例 ③ 段已写 `proxy_buffering off; proxy_cache off; gzip off;`）。
- **另一个上限**：gunicorn `--timeout 120`（systemd 样例）。流超过 120s 会被 worker 杀掉，
  Nginx 写 300s 只是"别比后端先断"。
- **怎么查**：直接用 curl 打流式接口（流程第 9 步），看是不是分块出现。

### 2.5 上传体积：Nginx 默认 1m，会在反代层 413

- 本项目真实上限（逐个从代码核对）：
  - 识别图 / 新闻图 / 帖子插图 / 助手提问图：**5MB**（`backend/api/image_validation.py:37`
    的 `MAX_IMAGE_SIZE`）；
  - 头像：**2MB**（`backend/api/views_user.py:343` 的 `MAX_SIZE`）；
  - Django 请求体：`DATA_UPLOAD_MAX_MEMORY_SIZE` **20MB**、`FILE_UPLOAD_MAX_MEMORY_SIZE` **10MB**
    （`settings.py:269`、`:272`）。⚠️ 后两个**不是硬上限**：`FILE_UPLOAD_MAX_MEMORY_SIZE` 只决定
    "超过多大就落临时文件"，真正拒绝超大文件的还是上面那两处业务校验。
- 样例给 `client_max_body_size 12m`：足够 5MB 图片 + multipart 边界/表单字段，又比 Django 的 20MB 小。
- **症状**：前端报一句笼统的错误，Nginx access log 里 413，Django 日志里**什么都没有**
  （请求根本没到 Django，所以拿不到"图片不能超过 5MB"这句可读提示）。

### 2.6 `ALLOWED_HOSTS` / `X-Forwarded-Proto` / 无限重定向

- `settings.py:262`：`SECURE_PROXY_SSL_HEADER = ('HTTP_X_FORWARDED_PROTO', 'https')`；
  `settings.py:247`：生产默认 `SECURE_SSL_REDIRECT=True`。
- 反代**不传** `X-Forwarded-Proto` 时：Django 认为所有请求都是 http → 301 到 https →
  浏览器走 https 又被判断成 http → **无限重定向**（`ERR_TOO_MANY_REDIRECTS`）。
  样例里每个 proxy 段都带了这个头，别删。
- 不传 `Host $host` 时：Django 收到 `Host: 127.0.0.1:8000`，与 `ALLOWED_HOSTS` 不匹配 → 400。
- 内网 http 部署（无证书）时，要把 `DJANGO_SECURE_SSL_REDIRECT=False`、
  `DJANGO_COOKIE_SECURE=False` 显式设回去（默认值是"安全的那一侧"）。

### 2.7 多 worker 下限流**静默失效**（缓存）

- 不是性能问题，是**功能正确性**：DRF 的限流计数存在 Django cache 里，
  默认 `LocMemCache` 是**进程内**的。3 个 worker = 限额被放大 3 倍，**没有任何报错**。
- 生产设 `.env` 里 `DJANGO_CACHE_URL=redis://127.0.0.1:6379/1`（见 `settings.py:451`）。
  不设时启动会 `warnings.warn`，`manage.py check_env` 与 `/api/health/` 也会标 `degraded`。
- 3 个 worker 时 `ASSISTANT_RATE_PER_MINUTE=10` 实际约 **30 次/分钟** —— 这是最容易没有察觉的一条。

### 2.8 前端 `dist` 的 API 地址是**构建期写死**的

- `frontend/src/api/assistant.js:58`：
  `const BASE_URL = (import.meta.env.VITE_API_BASE_URL || 'http://127.0.0.1:8000/api').replace(...)`
  —— 不传变量时，构建产物里就是**字面量** `http://127.0.0.1:8000/api`。
- 本次核对时仓库里的 `frontend/dist/assets/index-_g0Z5FGP.js` 能搜到 **3 处** `127.0.0.1:8000`，
  说明它是按开发地址构建的产物，**不能直接挪到服务器用**。
- 正确做法：`VITE_API_BASE_URL=/api npm run build-only`（同域部署用相对路径）。
- 检查：`grep -rl "127.0.0.1:8000" frontend/dist/assets/` 应为空。
- 症状：页面能打开、静态资源正常（同域），但所有接口都失败，浏览器控制台里请求打到 `127.0.0.1:8000`。

### 2.9 `.env.production.example` 里有四个"写了也不生效"的变量

- 下列四个在 `settings.py` 里**找不到任何读取点**（本次逐项 grep 过）：
  `DJANGO_CORS_ALLOWED_ORIGINS`、`DJANGO_CSRF_TRUSTED_ORIGINS`、
  `DJANGO_SESSION_COOKIE_SECURE`、`DJANGO_CSRF_COOKIE_SECURE`。
- 实际生效的是：`DJANGO_CORS_ALLOW_ALL`（`settings.py:194`）与 `DJANGO_COOKIE_SECURE`
  （`settings.py:227`，同时决定 CSRF Cookie 的 Secure）；而 `CORS_ALLOWED_ORIGINS`
  （`:196`）与 `CSRF_TRUSTED_ORIGINS`（`:765`）是**写死在代码里**的 localhost 列表。
- 影响：**同域部署**（前端和 `/api/` 同一个域名，本样例就是）完全不受影响 —— 不需要 CORS。
  只有"前端在 A 域、API 在 B 域"时才需要改代码（不在本次范围内）。
- 这几行留着不报错、也不生效，容易让人误以为"配了 CORS"。部署时知悉即可。

### 2.10 另外三个小坑

- **`/admin` 被 SPA 回退吃掉**：只写 `location /` 的话，`https://example.com/admin` 会拿到前端页面
  （一个 200 的网页，看起来"正常"）。样例里补了 `location /admin/` 和 `location = /admin`。
- **`sw.js` 不能长缓存**：`frontend/dist/sw.js` 是 PWA Service Worker（第 51 批）。
  给它 `max-age` 一年会让用户长期停在旧 SW 上，表现是"发版后部分页面还是老样子，清缓存才好"。
  样例里 `location = /sw.js { expires -1; }`；`index.html` 同理必须回源。
- **定时任务的命令名与时间**：见流程第 10 步的 ⚠️ —— `crontab.example` 里的
  `cleanup_media` / `process_deletions` 在当前代码里不存在，实际是 `prune_media` /
  `purge_deletion_requests`；且两处文档的时间不一致。

## 5. 哪些地方必须"按实际调整"

本文与样例里的数值分两类：**从代码核对来的**（可以直接信）和**环境相关的占位符**（必须改）。
后者清单：

| 位置 | 占位值 | 说明 |
|---|---|---|
| 两个配置文件的路径 | `/srv/crop-disease-system` | 部署到别处就整体替换（systemd 文件里 7 处、Nginx 文件里 9 处，含注释） |
| `server_name` / 证书路径 | `example.com` | 换成真实域名；证书路径随签发方式变 |
| systemd 的 `User=` / `Group=` | `crop` | 换成你的运行用户，**不要用 root** |
| gunicorn `--workers` | `3` | 每个 worker 带一份 YOLO（实测 ~700MB）；内存 < 4GB 改成 2 |
| `client_max_body_size` | `12m` | 改了业务上传上限就同步改 |
| 定时任务里的 `PY` / `APP` / `LOG` | 见 `crontab.example` | 还要把 `cleanup_media` / `process_deletions` 换成实际命令名 |
| 移动端 `/m/` 段 | 注释状态、**未实测** | 本次只核对了 `frontend/dist`，启用前请实际打开验证 |
| `VITE_API_BASE_URL` | `/api` | 前后端不同域时改成完整地址（并处理 2.9 的 CORS） |
| Node 版本 | 20.19+ / 22.12+ | Vite 7（`rolldown-vite`）的要求，构建机先 `node -v` |
| 数据库 | sqlite | 生产建议 PostgreSQL；sqlite 在并发写下会锁库 |
