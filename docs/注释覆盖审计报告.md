## 七、建议的补注释顺序（按"接手成本"排）

### 第 1 档：不补就会让人改错代码（约 1~2 小时）

这些不是"注释不够漂亮"，而是**读的人会做出错误判断**：

1. `mobile/src/utils/image.js` → `compressImage`：把每个阈值为什么是那个数写清楚
   （300KB 跳过、GIF 排除、强制 JPEG 的代价）。同时说明它与 `UPLOAD_LIMIT` 的关系。
2. `mobile/src/components/CameraCapture.vue` → `start`：补上桌面端已有的说明，
   并**明确写下**"移动端对所有失败都 emit unsupported，桌面端只对三种"——这是有意还是遗漏。
3. `frontend/src/views/PostDetailView.vue` → 回复分页簇 + `totalComments`：
   标成"已弃用/待接线"或直接删掉。**留着不标记比没有更危险**（会被当成坏了的功能去修）。
4. 移动端三份压缩配置：在一处写明"移动端标准值以 X 为准"，另两处加交叉引用。
5. `frontend/src/views/HomeView.vue` → `diseaseKeys`：说明这四组标签是 ML 数据集类别名、
   当前**没有**被消费；`diseaseCount` 是手工维护的。

### 第 2 档：文件级说明（约 2~3 小时，收益最广）

给这 10 个文件在脚本区/模块开头各加 5~10 行"这个文件是什么、由哪几块组成、改它要注意什么"：

```

frontend/src/views/HistoryView.vue
frontend/src/views/UserProfileView.vue
frontend/src/views/PreventionView.vue
frontend/src/views/HomeView.vue
```

### 第 3 档：大接口的契约说明（约 2 小时）

给第二节表里的 15 个方法各加一段 docstring：**输入 / 返回结构 / 失败形态 / 权限要求**。
其中 `LoginView.post`、`DetectView.post`、`AIService.predict` 收益最高。

### 第 4 档：顺手就做的（随时）

- 三个"零注释"文件：`frontend/src/components/PestImportDialog.vue`（密度 0.6%）、
  `frontend/src/components/OfflineIndicator.vue` 与它的移动端孪生（2.2% / 3.1%）；

  （它们是"数据从哪来"的答案，现在都要靠读代码猜）；
- `frontend/src/views/ConsultView.vue` 的 `page_size: 20` 与"没有分页控件"这件事。

### 不需要动的

- `backend/crop_disease_backend/settings.py`（70.5%）、`models.py`（23%）、`urls.py`（49.3%）

## 八、反向发现：不只是"缺注释"，还有 583 处**翻译式注释**

审计顺带查出另一个方向的毛病：**有些注释只是把代码念了一遍，没有提供任何新信息**。

```python
from django.contrib import admin          # 导入Django管理后台模块
from .models_forum import ForumBoard, …   # 导入论坛模型
def get_category_display(self, obj):      # 定义获取类别显示名称方法
    return obj.get_category_display()     # 返回类别显示名称
image_preview.short_description = '图片预览'   # 设置字段显示名称
if obj.image:                             # 检查图片是否存在
```

这类注释的危害不是"占地方"，而是**稀释**：当一屏里 80% 的注释都是废话时，
真正说明"为什么"的那 20%（例如 `# 第 38 批：给版主发通知时需要`）就很容易被跳过。
同一个文件里这两种注释是混在一起的 —— 上面那段抽样的 L26 与 L30 就是有价值的，
而 L21、L22、L28 是废话。

**统计（同一套正则，见下）**：

| 文件 | 翻译式注释 |
|---|---:|
| `backend/api/views_forum.py` | 174 处 |
| `backend/api/serializers.py` | 110 处 |
| `backend/api/serializers_forum.py` | 36 处 |
| `backend/api/models.py` | 33 处 |
| `backend/api/models_forum.py` | 33 处 |
| `backend/api/admin.py` | 32 处 |
| **全后端合计** | **583 处** |

> 判据：注释长度 ≤14 字，且形如 `# 导入… / # 设置… / # 定义… / # 获取… / # 返回… / # 检查…`。
> 这是**启发式**，会有误判（比如 `# 返回空数组如果解析失败` 也匹配，但那句其实有用）。
> 所以这份数字的用途是**定位**，不是"照着删 583 处"。

**怎么处理**：不建议批量删（会连有用的注释一起删掉）。建议**改到这些文件时顺手清理**，
清理原则是作者们已经写在《系统完善记录》里的那条约定：
> 注释解释"为什么"，不解释"是什么"。

具体到操作：`serializers.py` / `views_forum.py` 这类文件在做第 2 档（补文件级说明）时，
**一并把翻译式注释换成说明理由**，而不是简单删除 —— 例如
`image_preview.short_description = '图片预览'  # 设置字段显示名称`
可以改成
`# Django admin 的列标题：不能用 i18n（admin 是内部工具，固定中文更好找）`，
但前提是它真的有这个理由；没有理由就删掉。

## 十、⚠️ 审计顺带查出的 5 个真 bug（不是注释问题）

> **✅ 本节 5 条已在第 106 批全部修复**，每条都补了回归测试。
> 修复记录见《系统完善记录》第一百节；这里保留原始诊断，便于对照。

**这一节是本报告最重要的部分。** 逐文件读代码时发现的问题，其中 3 个我已独立核实到
"能稳定复现"或"代码路径确定"，2 个是静态分析结论（未跑代码）。

### 1. `POST /api/forums/likes/` 会把点赞数**多算 1**（已实测复现）

```
点赞前：like_count=0  真实行数=0
POST /api/forums/likes/  → HTTP 201
点赞后：like_count=2  真实行数=1     ← 差 1
```

原因：**一次请求里有两个人写同一个计数字段**。

```python
# models_forum.py:303-317  Like.save()（被下面的 create 触发）
post.like_count = Like.objects.filter(post_id=self.post_id).count()   # 设成"真实行数"= 1
post.save(update_fields=['like_count'])

# views_forum.py:1279-1283  LikeViewSet.create
like = Like.objects.create(user=request.user, post=post)              # ← 触发上面的 save
post.like_count = F('like_count') + 1                                 # ← 又 +1 → 2
post.save(update_fields=['like_count', 'updated_at'])
```

`Like.save()` 已经把计数**精确重算**过了，视图再 `+1` 就是叠加。
**影响范围有限**：前端点赞走的是 `PostViewSet.like`（`/forums/posts/{id}/like/`），
不是这个接口 —— 所以线上没暴露。但 `POST /api/forums/likes/` 是**公开可用的接口**，
任何直接调它的客户端都会把数据写坏。
> 顺带说明：同文件 L1285-1290 的注释记录过"这里原本调用一个不存在的方法导致必定 500"，
> 那个问题已经修了 —— 但**没人注意到紧接着的计数逻辑也是错的**。

### 2. `/api/pest-types/?search=` 必定 500（字段不存在）

```python
# views.py:2525-2530  PestTypesView.get
queryset = queryset.filter(
    Q(name__icontains=search) |
    Q(english_name__icontains=search) |     # ← PestInfo 没有这个字段
    Q(description__icontains=search)
)
```

核实过：`PestInfo` 只有 `name` 与 `english_identifier`，**没有 `english_name`**。
`FieldError` 被外层 `except Exception` 吞掉 → 返回 500「获取病害类型失败」。

**最值得注意的不是这个 bug，而是它的"孪生兄弟已经修好了"**：

```python
# views.py:945-947  PreventionDataView.get（同一个文件，早在第 78 批就修了）
# 注意：PestInfo 没有 english_name 字段（只有 name 与 english_identifier），
# 原来这里写 Q(english_name__icontains=...) 会抛 FieldError，
# 导致「带 search 参数」的请求必定失败。
```

**修复和解释都做了，但没有人把它传播到另一个方法。** 这正是"注释只写在一处"的代价。

### 3. 密码最小长度有三套，且重置密码能绕过全部规则

| 位置 | 最小长度 | 其它规则 |
|---|---|---|
| 注册（`serializers.py:299`） | 6 | — |
| 邮箱重置（`views_user.py:180`） | 6 | **一条都没有** |
| 修改密码（`views_user.py:348/382`） | **8** | 不能纯数字、不能与旧密码相同 |

后果：用户可以**通过邮箱把密码重置成 `123456`**，但在"修改密码"页面**不能**把它改成 `123456`
（也不允许改成纯数字）。而 `settings.py:288-301` 的 `AUTH_PASSWORD_VALIDATORS`
**整段被注释掉了且没有写原因** —— 三套规则各自为政，没有一处说明哪个才是策略。

### 4. 取消注销接口是**匿名且无限流**的密码校验端点

`views_user.py:502-503`：`permissions.AllowAny` + `authentication_classes = []`，
**没有 `throttle_classes`**。

而第 91 批移除 DRF 自带 `/api/token-auth/` 时的理由（`urls.py:175-183`）正是：
> "改打这个端点就能无限撞库"

—— `AccountCancelDeletionView` 属于**同一类**：给个用户名+密码就回答"对不对"，
不限速、不计失败次数。它上面三行的 docstring 还专门解释了"为什么失败文案必须一致以防账号枚举"，
**但没提限流**。这是本次审计发现的安全面最重的一条。

### 5. `views.py` 里有一个**永远走不到**的重复 `NewsViewSet`（含一个必定 500 的 action）
