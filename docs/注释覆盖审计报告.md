## 八、反向发现：不只是"缺注释"，还有 583 处**翻译式注释**

审计顺带查出另一个方向的毛病：**有些注释只是把代码念了一遍，没有提供任何新信息**。

```python
from django.contrib import admin          # 导入Django管理后台模块
from .models_forum import ForumBoard, …   # 导入论坛模型
def get_category_display(self, obj):      # 定义获取类别显示名称方法

```

这类注释的危害不是"占地方"，而是**稀释**：当一屏里 80% 的注释都是废话时，
真正说明"为什么"的那 20%（例如 `# 第 38 批：给版主发通知时需要`）就很容易被跳过。
同一个文件里这两种注释是混在一起的 —— 上面那段抽样的 L26 与 L30 就是有价值的，
而 L21、L22、L28 是废话。

**统计（同一套正则，见下）**：

| 文件 | 翻译式注释 |
|---|---:|
| `backend/api/views_forum.py` | 174 处 |
| `backend/api/serializers.py` | 110 处 |
| `backend/api/serializers_forum.py` | 36 处 |
| `backend/api/models.py` | 33 处 |
| `backend/api/models_forum.py` | 33 处 |
| `backend/api/admin.py` | 32 处 |
| **全后端合计** | **583 处** |

> 判据：注释长度 ≤14 字，且形如 `# 导入… / # 设置… / # 定义… / # 获取… / # 返回… / # 检查…`。
> 这是**启发式**，会有误判（比如 `# 返回空数组如果解析失败` 也匹配，但那句其实有用）。
> 所以这份数字的用途是**定位**，不是"照着删 583 处"。

**怎么处理**：不建议批量删（会连有用的注释一起删掉）。建议**改到这些文件时顺手清理**，
清理原则是作者们已经写在《系统完善记录》里的那条约定：
> 注释解释"为什么"，不解释"是什么"。

具体到操作：`serializers.py` / `views_forum.py` 这类文件在做第 2 档（补文件级说明）时，
**一并把翻译式注释换成说明理由**，而不是简单删除 —— 例如
`image_preview.short_description = '图片预览'  # 设置字段显示名称`
可以改成
`# Django admin 的列标题：不能用 i18n（admin 是内部工具，固定中文更好找）`，
但前提是它真的有这个理由；没有理由就删掉。

### 1. `POST /api/forums/likes/` 会把点赞数**多算 1**（已实测复现）

```
点赞前：like_count=0  真实行数=0
POST /api/forums/likes/  → HTTP 201
点赞后：like_count=2  真实行数=1     ← 差 1
```

原因：**一次请求里有两个人写同一个计数字段**。

```python
# models_forum.py:303-317  Like.save()（被下面的 create 触发）
post.like_count = Like.objects.filter(post_id=self.post_id).count()   # 设成"真实行数"= 1
post.save(update_fields=['like_count'])

# views_forum.py:1279-1283  LikeViewSet.create
like = Like.objects.create(user=request.user, post=post)              # ← 触发上面的 save
post.like_count = F('like_count') + 1                                 # ← 又 +1 → 2
post.save(update_fields=['like_count', 'updated_at'])
```

`Like.save()` 已经把计数**精确重算**过了，视图再 `+1` 就是叠加。
**影响范围有限**：前端点赞走的是 `PostViewSet.like`（`/forums/posts/{id}/like/`），
不是这个接口 —— 所以线上没暴露。但 `POST /api/forums/likes/` 是**公开可用的接口**，
任何直接调它的客户端都会把数据写坏。
> 顺带说明：同文件 L1285-1290 的注释记录过"这里原本调用一个不存在的方法导致必定 500"，
> 那个问题已经修了 —— 但**没人注意到紧接着的计数逻辑也是错的**。

### 2. `/api/pest-types/?search=` 必定 500（字段不存在）
