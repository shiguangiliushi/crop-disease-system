# 备份与恢复

> 第 102 批新增。在此之前项目里**没有任何可用的完整备份手段** ——
> 唯一存在的 `forum_backup` 命令一跑就崩，只覆盖论坛 5 张表，还把备份写进 `media/`。
> 这份文档写清"怎么备、怎么验、怎么恢复、怎么演练"，并且**每一步都有实测结论**。

---

## 一、先看结论：三分钟上手

```bash
cd backend

# 备份（库 + media，默认写到 项目根/backups）
python manage.py backend_backup

# 校验（校验和 + 库完整性 + 真实条数 + 媒体包结构）
python manage.py backup_verify --strict        # 有问题退出码 1

# 看看有哪些备份、都是什么时候的
python manage.py backend_restore --list

# 恢复（**不加 --yes 只打印计划，不写任何数据**）
python manage.py backend_restore 20261004-024456 --yes
```

## 二、备份了什么

| 产物 | 内容 | 为什么 |
|---|---|---|
| `db.sqlite3` | 数据库副本 | 用 **SQLite 在线备份 API** 取一致性快照 |
| `media.tar.gz` | 全部用户上传（头像/识别图/帖子配图/新闻图…） | 打成包 + 记校验和，才能被校验 |
| `data.json` | `dumpdata` 文本摘要 | sqlite 文件损坏时的**最后一道救命绳**（可跨库读） |
| `models.tar.gz` | 模型权重（`--include-models`） | 默认不含：权重是外部资产，且约 20MB |
| `manifest.json` | 体积、sha256、**各业务表条数** | 让"这份备份能不能用"可验证 |

### 为什么不用 `cp db.sqlite3`

服务运行中直接复制文件，可能拿到**写事务中间**的状态 ——
恢复时报 `database disk image is malformed`。`sqlite3.Connection.backup()` 是
SQLite 官方的在线备份接口，会取一致性快照。备份命令还会顺手在源库上跑
`PRAGMA integrity_check`：**备份一个已经损坏的库没有意义**。

### 为什么备份不放在 `media/` 里

旧的 `forum_backup` 把备份写进 `MEDIA_ROOT/forum_backups/` —— 和要保护的数据放在
同一个目录。`media` 是最容易被"清理上传目录""rsync --delete""容器改挂载"碰到的地方，
备份放进去等于把鸡蛋放在同一个篮子里。默认位置是**项目根/backups**，
生产请用 `DJANGO_BACKUP_DIR` 指到**另一块盘或网络存储**。

## 三、备份的"可用性"是要验证的

`backup_verify` 不做"看一眼文件在不在"这种事，它**真的把备份读一遍**：

1. 清单在不在、**格式版本**对不对；
2. 每个产物的 **sha256 与清单是否一致** —— 这一条能抓出截断、静默损坏、被改动；
3. **把备份里的库打开**跑 `PRAGMA integrity_check`，并读出真实条数，
   与清单里记录的条数对比；
4. 媒体包**逐块读出**（不是只读索引 —— 只读索引的话截断的包照样能"列出成员"）。

实测输出：

```
校验 20261004-024456
  ✓ 清单可读（格式 v1，创建于 2026-10-03T18:44:56）
  ✓ db.sqlite3 校验和一致（2.0 MB，0.0s）
  ✓ media.tar.gz 校验和一致（17.3 MB，0.0s）
  ✓ data.json 校验和一致（372.8 KB，0.0s）
  ✓ 库完整性 OK，条数：users=4、detections=25、pests=38、posts=7、comments=14、boards=3、feedback=27、news=8
  ✓ 媒体包结构 OK（971 个文件，清单记录 971，0.3s）

全部校验通过：备份可用
```

## 四、恢复：默认是"换掉"，不是"合并"

| 模式 | 行为 | 适用场景 |
|---|---|---|
| **replace（默认）** | 用备份里的库**整体替换**当前库；媒体**只补缺失文件** | "数据被删了/库坏了，回到备份那一刻" |
| `--merge` | 保留当前库，把备份里的行**按主键补进去**（不覆盖已有记录） | "只想把某些丢失的记录捞回来" |

为什么默认 replace：备份的语义就是"那一刻的快照"。默认 merge 会让人以为"恢复完成了"，
实际库里是两批数据混在一起，**比明确替换更难排查**。

### 四道安全网

1. **必须显式 `--yes`** —— 没有它只打印计划。
   （旧 `forum_backup restore` 用 `input()` 交互确认：定时任务/管道里会**直接卡死**，
   而任何人误敲回车就开删。）
2. **先校验备份** —— 恢复一份损坏的备份 = 用坏数据覆盖好数据，
   是**把事故从"数据丢了"升级成"数据彻底没了"**。校验不过直接中止（退出码 1）。
3. **恢复前自动做一份快照**（`--label pre-restore`）—— 万一备份不是想要的那一份，还能退回来。
4. **旧库另存为 `db.sqlite3.pre-restore`**，再写新库。

### 恢复之后必须做的一件事

```bash
# 重启后端进程
```

SQLite 连接与 Django 缓存里可能还留着旧状态。命令输出里也会提醒这一点。

## 五、定时任务（不挂 = 备份等于没做）

```cron
# 每天 03:00 备份，只留最近 30 份
0  3 * * *  cd /path/to/backend && /path/to/python manage.py backend_backup --keep 30 --quiet
# 每天 03:30 校验最新一份，有问题退出码非 0（接告警）
30 3 * * *  cd /path/to/backend && /path/to/python manage.py backup_verify --strict
```

Windows（任务计划程序）：

```powershell
$action  = New-ScheduledTaskAction -Execute "C:\...\python.exe" `
  -Argument "manage.py backend_backup --keep 30 --quiet" -WorkingDirectory "D:\...\backend"
$trigger = New-ScheduledTaskTrigger -Daily -At 3am
Register-ScheduledTask -TaskName "crop-backup" -Action $action -Trigger $trigger
```

`manage.py check_env` 会检查备份新鲜度并在过期时报警：

```
⚠ 最新备份已 4.2 天前：定时任务可能没跑，请检查
⚠ 没有任何备份（…\backups 下为空）：请跑 `manage.py backend_backup`
```

### 分层的"3-2-1"落地建议

| 层 | 做法 |
|---|---|
| 本地快照 | 上面这个 cron + `--keep 30`（防误删/误操作） |
| 异地一份 | 把 `backups/` 同步到另一台机器或对象存储（防磁盘/整机故障） |
| 离线一份 | 每周手工拷一份到移动硬盘（防勒索软件） |

## 六、恢复演练（**必须做，否则不算有备份**）

"有备份"和"能恢复"是两件事。**第 154 批把这份演练固化成了命令**，随时可以重跑：

```bash
cd backend
python manage.py backup_drill            # 只打印计划（不带 --yes 什么都不做）
python manage.py backup_drill --yes      # 真演练：造标记物 → 备份 → 破坏 → 恢复 → 逐项验证
python manage.py backup_drill --yes --keep        # 保留那次演练备份
python manage.py backup_drill --yes --skip-media  # 只演练数据库（更快）
```

它做的正是下面这五步，并给出**逐项 PASS/FAIL**（任一项不过就以退出码 1 结束，
并保留演练备份供你排查）：

```
① 造两样"独有的东西"：一条特殊标题的帖子 + 一张独有的上传图片（记下 sha256）
② 备份（backend_backup --label drill）
③ 破坏：删掉那条帖子、删掉那张图片、删掉一批识别记录
④ 恢复（backend_restore <名字> --yes --overwrite-media）
⑤ 验证：帖子回来了、图片回来了且**校验和一致**、识别记录条数回到备份时的值
```

> ⚠️ 它会**改写数据库**，所以门开得很窄：
> **必须 `--yes`**；**默认只允许 `DEBUG=True`**（生产要演练请用另一套数据/另一台机器，
> 确实要在生产跑得加 `--force`，并清楚这几秒内别人的写入会被回滚）。
> 首次跑之前建议先**停掉 `runserver`**（恢复后 Django 缓存里可能还留着旧状态）。
>
> 第 154 批的实测结果：**7/7 项通过**（详情见 `系统完善记录.md` 第 154 批）——
> 这是"这套备份确实能恢复"的凭证，而不是"我记得上次是好的"。
>
> 顺带修掉一个**真实的数据泄露风险**：`backend_restore` 在替换数据库前会把旧库另存为
> `db.sqlite3.pre-restore`（含真实用户表与口令哈希），而 `db.sqlite3` 的忽略规则
> **匹配不到它**。演练跑完它曾出现在 `git status` 的未跟踪列表里 —— 谁用 `git add .`
> 谁就可能把它推上公开仓库。现在 `.gitignore` 已覆盖 `*.pre-restore`，
> 演练成功后也会自己删掉它。

实测结果（第 102 批）：

```
✓ 备份校验通过（--strict 退出码 0）
✓ 图片文件已删除（模拟丢文件）
  恢复后条数：users=5、detections=26、pests=38、posts=8、comments=14、boards=3、feedback=27、news=8
✓ 被删的帖子回来了
✓ 帖子内容完整
✓ 被删的识别记录回来了
✓ 识别记录条数回到备份时的值 — 现在 26 / 备份时 26
✓ 丢失的图片文件被恢复
```

**建议每季度做一次**，尤其是：升级 Django / 改模型之后、换机器之后、换数据库之后。

## 七、media 孤儿文件清理（第 106 批）

备份会把 `media/` 里**所有**文件一起备走 —— 包括那些**没有任何数据库引用**的文件。
它们不致命，但会白占磁盘，而且**只增不减**。第 104 批（E2E 残留）与
第 105 批（注释审计）各查出一次，于是有了这个命令：

```bash
python manage.py prune_media                          # 只报告（默认干跑）
python manage.py prune_media --yes                    # 真删
python manage.py prune_media --min-age-days 0 --yes   # 连刚落的文件一起清（测试用）
python manage.py prune_media --dir detection_uploads  # 只清某个子目录
```

### 为什么默认是干跑

和恢复命令同一个约定：**危险操作默认什么都不做**。
不加 `--yes` 时只打印报告 + 把清单写到系统临时目录，万一误删还能对照。

### 三条保护规则

| 规则 | 为什么 |
|---|---|
| 只删**没有任何 FileField 引用**的文件 | 引用集合是**遍历 `apps.get_models()` 自动收集**的，不是手写清单 —— 新增带图片的模型时没人会记得回来改这个命令，那样新模型的文件就会被当垃圾删掉 |
| 只删**超过 `--min-age-days`（默认 7 天）**的文件 | **正在上传、还没入库的文件看起来也像孤儿**，这个命令不该和业务抢文件 |
| 引用比对同时认**反斜杠路径**与**完整 URL** | 历史数据里两种都存在（`detection_uploads\x.JPG` / `http://host/media/x.jpg`），不归一就会误删 |

### 实测演练（第 106 批，对真实开发库）

```
无引用且超过 0 天的文件：791 个（10.3 MB）
已删除 791 个文件（10.3 MB），清理空目录 2 个
media：897 个文件 → 106 个文件 / 6.61 MB
```

**删之前的假阳性检查**（这一步比删除本身重要）：

1. 扫全库"非 FileField 但存了文件路径的列" → 0 处；
2. 前端/移动端源码里硬编码这些文件名 → 0 处；
3. **先把整个 media 备份一份**再执行；
4. 删完重新清点：数据库引用的 116 处里"文件不存在"的有 10 处 ——
   逐条核对发现**它们在备份里也不存在**，是审计夹具留下的悬空引用（文件从来没被创建过），
   **不是 prune 删的**；
5. 关键页面接口实测：病害百科 / 识别记录 / 新闻全部 200，图片实际可下载。

### 根因（这批一并修了，否则删完还会再长出来）

| 根因 | 修复 |
|---|---|
| `DetectionHistory.annotated_image` 字段一直存在，但识别接口**从来没写过值** —— 标注图落盘后无人认领 | 识别时把路径一并入库；迁移 `0043` 把历史漏掉的补回（补回 0 条、跳过 27 条） |
| 识别接口把同一张上传图**写了两遍**（同一路径、同一迭代器），第二遍的注释还写着"保存到临时位置" | 删掉重复写盘（两次写之间只有"AI 服务是否初始化"的判断，不通过就 return） |

### 挂上定时任务

```cron
# 每天 04:00 清理（必须带 --yes，否则只报告不删）
0 4 * * *  cd /path/to/backend && /path/to/python manage.py prune_media --yes --min-age-days 7
```

⚠️ **不挂不会立刻出事，但 `media/` 会只增不减地长** —— 上面那个实测就是长出来的结果。
而且它**没有"新鲜度"概念**，所以 `check_env` 发现不了"这个任务没在跑"，
只能靠记住它。**五件**定时任务的完整清单见 [部署与运维.md](部署与运维.md)
（备份 / 校验 / 健康快照 / media 清理 / 注销到期执行；第 219 批核对时补齐了 `health_snapshot`）。

## 八、已知限制（如实说明）

| 限制 | 说明 |
|---|---|
| **只支持 SQLite** | 命令会明确拒绝 PostgreSQL/MySQL（提示改用 `pg_dump`/`mysqldump`）。当前项目用的就是 sqlite，所以够用；换库时要改这套脚本。 |
| `data.json` 与库副本不是同一毫秒的快照 | 摘要走 `dumpdata`（读当前连接），与在线备份之间有一瞬间的窗口。**它是补充**，恢复以库副本为准；真要抢救数据时按"尽量新的那份"取。 |
| **恢复期间服务未停** | 恢复是文件级替换，运行中的进程可能仍持有旧库句柄。命令会提示重启；生产建议先停服务再恢复。 |
| 媒体默认不覆盖 | 这是有意的（避免把较新的上传覆盖回旧版本），需要覆盖时显式 `--overwrite-media`。 |
| 模型权重默认不含 | 它们是外部资产（`api/newmodels/best.pt` 等，约 20MB），用 `--include-models` 才打包。 |
| 日志：Windows 上并发轮转会被**跳过**（不丢日志） | 第 107/118 批起日志用 `api.log_handlers.SafeRotatingFileHandler`：`logs/debug.log` 被运行中的进程占用时，它会重试 20 次，仍抢不到就**跳过这次轮转、继续往原文件追加**，并进入 30 秒冷却（日志里能看到"本次跳过轮转并冷却 30 秒"）。<br>所以**不再抛异常、也不丢日志**，代价是文件可能暂时超出 `maxBytes`；`WinError 32` 只会出现在底层 rename 处且已被捕获。Linux 部署一般不触发。 |
