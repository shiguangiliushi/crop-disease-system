# 部署与运维指南

> 第 94 批新增。此前项目里**没有任何生产启动方式**：全仓没有 Dockerfile、没有 gunicorn 配置、
> 没有 Nginx 配置，`requirements.txt` 只有 8 行且**照它装不出能跑的环境**。
> 这份文档把"从零到能访问"的每一步写清楚，并附上这一轮真实踩到的坑。

---

## 一、部署前先跑一次环境自检

```bash
cd backend
python manage.py check_env            # 人看的报告
python manage.py check_env --strict   # 有问题就退出码 1（可放进 CI）
```

它会检查六件事，**每一项都对应过一次真实事故**：

| 检查 | 为什么要有这一条 |
|---|---|
| 依赖包版本对照 `requirements.txt` | 那个文件曾经缺 `django-cors-headers` / `django-filter`，且版本与开发环境全不一样 |
| `INSTALLED_APPS` 里的第三方应用能否导入 | 同上 —— 装了才算数 |
| 数据库 / 缓存 / 迁移 / 模型文件 / 媒体目录可写 | "服务起来了但迁移没跑"是最常见的上线故障 |
| 生产开关（DEBUG / ALLOWED_HOSTS / HTTPS / 邮件后端） | 只提示不拦截：开发环境本来就该是 DEBUG=True |

## 二、环境变量

模板在 `backend/.env.example`，复制成 `backend/.env` 后按需填：

```bash
cp backend/.env.example backend/.env
# 生产至少填这三项：

#   DJANGO_DEBUG=False

#   DJANGO_SECRET_KEY=<50 位随机串>     ← 不填会**直接拒绝启动**（有意为之）

#   DJANGO_ALLOWED_HOSTS=example.com,10.0.0.5

python -c "from django.core.management.utils import get_random_secret_key as g; print(g())"
```

优先级：**真实环境变量 > `.env` 文件 > 代码里的开发默认值**。

### 生产相关的开关（第 94 批新增）

| 变量 | 默认 | 说明 |
|---|---|---|
| `DJANGO_SECURE_SSL_REDIRECT` | 生产 `True` | http 请求 301 到 https。**内网 http 部署要显式设 False**，否则无限重定向 |
| `DJANGO_SECURE_HSTS_SECONDS` | `0` | HSTS。默认关 —— 浏览器会记住 max-age，**确认 HTTPS 稳定后再开** |
| `DJANGO_COOKIE_SECURE` | 生产 `True` | 只在 HTTPS 下发会话/CSRF Cookie |
| `DJANGO_USE_X_FORWARDED_HOST/PORT` | 生产 `True` | 有反代时开；没有反代就别开（可被伪造） |
| `DJANGO_SERVE_MEDIA` | `= DEBUG` | 生产是否由 Django 托管 `/media/`。没配 Nginx 的小规模部署设 `True` |
| `DJANGO_WHITENOISE` | 生产 `True` | 静态文件（admin 样式）由 WhiteNoise 托管；没装这个包自动跳过 |
| `DJANGO_TOKEN_TTL_SECONDS` | `604800` | Token 有效期（秒）。**`0` = 不过期**（仅开发用） |

## 三、三种部署方式

### 方式 A：单机 + gunicorn（最小可用，推荐先跑通这个）

```bash
cd backend
pip install -r requirements.txt -r requirements-prod.txt

> ⚠️ **先确认解释器**：`requirements.txt` 的版本是按项目约定的环境锁的。
> 若同一个仓库里还留着一份临时建的 `venv/`，用它跑 `check_env` 会报一串
> 「版本不符」—— 那是**环境不对**，不是包坏了（`check_env` 现在会先打印解释器路径，
> 以及它是否位于仓库目录内）。`backend/venv/` 是 gitignore 的本地残留，不要用它启动。

# 1) 准备环境

cp .env.example .env        # 填 DJANGO_SECRET_KEY / DJANGO_DEBUG=False / ALLOWED_HOSTS
#   内网 http 部署再补：DJANGO_SECURE_SSL_REDIRECT=False、DJANGO_COOKIE_SECURE=False

# 2) 建库与静态文件

python manage.py migrate
python manage.py collectstatic --noinput

# 3) 起服务（两个 worker；见 gunicorn.conf.py 里的调参说明）

gunicorn -c gunicorn.conf.py crop_disease_backend.wsgi:application

# 4) 验证

curl -i http://127.0.0.1:8000/api/health/          # 期望 200 {"status":"ok"}
curl -i "http://127.0.0.1:8000/api/health/?deep=true"   # 额外看迁移与模型
```

前端产物自己发（任选 Nginx / `python ../docs/tools/serve_spa.py` / 任意静态服务器），
反代 `/api`、`/media` 到 8000 即可。

### 方式 B：Docker Compose（后端 + Nginx + 两个前端）

```bash
# 1) 构建前端产物（Nginx 直接发 dist，不在容器里跑 node）

cd frontend && npm ci && npm run build-only && cd ..
cd mobile   && npm ci && npm run build      && cd ..

# 2) 准备后端环境变量

cp backend/.env.example backend/.env        # 至少填 DJANGO_SECRET_KEY

# 3) 起

docker compose up -d --build

# 4) 验证

curl -i http://localhost/api/health/
# 桌面端： http://localhost/

# 移动端： http://localhost/m/

```

`docker-compose.yml`、`backend/Dockerfile`、`deploy/nginx.conf` 都在仓库里。
数据库默认仍是 sqlite（挂卷持久化）；换 Postgres 的步骤写在 compose 文件末尾的注释里。

#### B-1. 三个"仓库里没有、线上必须有"的文件

| 文件 | 仓库里是什么 | 线上必须是什么 |
|---|---|---|
| `frontend/.env.production` | `VITE_API_BASE_URL=/api`（已入库，第 432 批补上） | 同左。**缺了就会把 `http://127.0.0.1:8000` 打进产物**，线上图片全裂 |
| `deploy/nginx.conf` | **HTTP-only 精简样板**（只有 `listen 80`） | 你的 HTTPS 版（`listen 443 ssl` + `ssl_certificate` + 域名 + no-cache 段） |
| `docker-compose.yml` | 只有 `80:80`、无证书挂载 | 加上 `"443:443"` 与 `./deploy/certs:/etc/nginx/certs:ro` |
| `backend/.dockerignore` | 排除 `db.sqlite3` / `media/` / `logs/` / `backups/` | 同左。**缺了会把生产数据烤进镜像**（见 §六.10） |

> ⚠️ 这两处（nginx.conf / compose）是**每台机器自己的**，不要用仓库版覆盖、也不要用 `.bak` 覆盖。
> 改完先 `cp` 一份到 `~/` 留档：
> ```bash
> cp deploy/nginx.conf  ~/nginx.conf.prod.$(date +%m%d)
> cp docker-compose.yml ~/docker-compose.prod.$(date +%m%d)
> ```

#### B-2. 构建前端：本机 Node 可能太老

项目要求 `node ^20.19 || >=22.12`（`package.json` 的 engines）。用 Node 18 会失败在

```
error during build: [plugin vite:vue] TypeError: crypto.hash is not a function
```

最稳的做法是**用容器构建**，不折腾本机 Node：

```bash
cd frontend
sudo docker run --rm -v $PWD:/app -w /app node:22-bookworm-slim sh -c "npx vite build"
sudo chown -R ubuntu:ubuntu dist
```

构建完**必须验一条**（0 才算对）：

```bash
grep -c "127.0.0.1:8000" dist/assets/*.js | grep -v ':0' || echo "✅ 产物无本机地址"
curl -s https://<域名>/ | grep -o 'assets/index-[^"]*\.js' | head -1   # 浏览器实际加载的
ls dist/assets/index-*.js | sed 's#.*/##' | head -3                    # 与上一行 hash 对得上
```

#### B-3. 部署顺序（顺序错了会 502）

```bash
# 1) 后端重建
sudo docker compose up -d --build backend

# 2) 必须跟一步重启 nginx —— 它启动时解析一次 upstream，backend 换 IP 后缓存不失效
sudo docker compose restart nginx

# 3) 等后端健康再验收
sleep 20
curl -s -o /dev/null -w "api:%{http_code}\n" https://<域名>/api/health/
sudo docker compose ps      # backend 要 Up (healthy)，nginx 要含 443
```

前端的 `dist` 是**目录挂载**（`./frontend/dist:/usr/share/nginx/html:ro`），重新构建后**不用重启 nginx**，浏览器强刷即可。

## 五、这一轮踩到的坑（都是"静默失败"型）

### 1. `django.conf.urls.static.static()` 在 `DEBUG=False` 下是**静默空操作**

```python
def static(prefix, view=serve, **kwargs):
    ...
    elif not settings.DEBUG or urlsplit(prefix).netloc:
        return []          # ← 生产下什么都不挂，且不报错
```

所以"用 `static()` 挂 `/media/` 到生产"是**配了等于没配** —— 页面表现是"图片全是碎的"，
而开发机上永远不会出现。正确做法是自己写 `re_path` 指向 `django.views.static.serve`：

```python
urlpatterns += [
    re_path(r'^%s(?P<path>.*)$' % re.escape(settings.MEDIA_URL.lstrip('/')),
            media_serve, {'document_root': settings.MEDIA_ROOT}),
]
```

（`serve` 自带 `safe_join`，实测 `/media/%2e%2e/db.sqlite3` 会被拦成 400。）

### 2. Token 过期"配了但不生效"

`TOKEN_EXPIRED_AFTER_SECONDS` 一直只有定义、**没有任何代码读它** ——
DRF 的 `TokenAuthentication` 不校验创建时间。所以"7 天过期"只是一句注释。
第 94 批在 `api/middleware.py` 里真正执行（过期即删、按未认证处理，带 `X-Token-Expired: 1`）。

**连带修掉一个更隐蔽的问题**：登录用的是 `Token.objects.get_or_create(user=...)`，
于是"过期但还没被用过"的 Token 会被原样返回 —— 用户密码输对了，拿到的却是失效凭证。
现在登录/注册一律 `delete()` + `create()`（顺带好处：登录即轮换，旧凭证立刻失效）。

### 3. 生产仍在用 LocMemCache

**限流计数器就存在缓存里** —— 多 worker 下每个进程各算一份，LocMem 会让限流形同虚设。
`check_env` 与 `/api/health/` 都会把这件事标出来（`degraded` / 提示语）。

第 153 批核对：缓存配置现在在 `settings.py` 有**五级优先级**
（`DJANGO_CACHE_URL` → `DJANGO_CACHE_BACKEND` → 测试用 LocMem →
`DEBUG=True` 用**文件缓存** `backend/cache/` → 生产才回落 LocMem 并 `warnings.warn`）。
所以**不用改代码**，设一个环境变量就行：

```bash
# .env / 部署环境里

DJANGO_CACHE_URL=redis://127.0.0.1:6379/1
```

```python
# 想显式指定后端也可以（等价于 DJANGO_CACHE_BACKEND）

# settings.py 会把它拼成 CACHES['default']，无需手写整个字典

```

> ⚠️ 开发环境（`DEBUG=True`）用的是**文件缓存**（`backend/cache/`），不是 LocMem ——
> 这样 `runserver --noreload` 重启进程也不会把限流计数清零。

### 4. Nginx 默认 `client_max_body_size 1m`

识别图允许 5MB —— 不改 Nginx 的话上传会在**反代层**就被 413 拒掉，
而且前端看不到 Django 的任何提示（`deploy/nginx.conf` 里已设成 12m）。

### 5. 生产控制台里的 WebSocket 报错是**客户端自导自演**（第 429 批）

现象（每次打开生产站点都出现，看起来像后端挂了）：

```
WebSocket connection to 'wss://<域名>/ws' failed
Max reconnection attempts reached, giving up
Failed to load resource: net::ERR_FAILED
```

根因：`frontend/src/main.js` 里留了一段"生产环境连 `/ws`"的代码（带 5 次指数退避重连），
**而后端从来没有 WebSocket 服务**：

| 需要的东西 | 实际情况 |
|---|---|
| ASGI 应用 | `asgi.py` 就是 `get_asgi_application()`，没有 Channels |
| WS 服务器（daphne / uvicorn） | 没有；`gunicorn -c gunicorn.conf.py crop_disease_backend.wsgi` 是 WSGI |
| 依赖 | `requirements.txt` 里没有 `channels` |
| 反代转发 | `deploy/nginx.conf` 里没有 `/ws` 的 `Upgrade` 配置 |
| 客户端处理 | 连 `onmessage` 都没有 —— 就算连上也什么都不做 |

所以它只会：每次页面加载白试 **6 次**（1+2+4+8+16 秒退避）、打 6 条报错、
浏览器再记一条资源加载失败，然后放弃。排查别的问题时全是噪音。已整段删除。

**真要做实时推送**，四件缺一不可，且顺序是先服务端后客户端：

1. 装 `channels`（+ `channels-redis` 做跨进程），把 `asgi.py` 换成
   `ProtocolTypeRouter({'http': get_asgi_application(), 'websocket': AuthMiddlewareStack(...)})`；
2. 用 daphne / uvicorn 起 ASGI（gunicorn 的 `sync` worker 不处理 WS）；
3. nginx 给 `/ws/` 加 `proxy_http_version 1.1` + `Upgrade` / `Connection` 头；
4. 客户端**先有 `onmessage` 再连**，并把"连不上"降级成一条 debug 日志，而不是 5 次重连。

另：同一份控制台里 `content.js:… detectPageLang` 那类日志来自**浏览器扩展**
（翻译/SEO 类），不在本仓库里，可以忽略。

### 6. Mixed Content：HTTPS 页面里的图片被拦（第 430 批）

现象（生产站控制台，每次加载都有 6 条左右）：

```
Mixed Content: The page at 'https://…' was loaded over HTTPS, but requested an
insecure image 'http://10.0.0.5/media/…' — This request has been blocked
```

用户看到的是**图片裂开**（不是 404，也不是报错弹窗）。而模板里并没有写死这个地址 ——
它来自**数据**：

| 来源 | 存的是什么 | 为什么会出现 |
|---|---|---|
| `ImageField` / `FileField` | `http://<服务器IP>/media/x.jpg` | 早期用局域网 IP 调试时写进去的；后来换域名、上 HTTPS 没跟着变 |
| 富文本正文（帖子/新闻/病害描述） | `<img src="http://…/media/…">` | 自己写的 HTML，绕过所有 `:src` 绑定 |

**为什么不能简单把 http 改成 https**：那个 host 往往是没有证书的 IP，
换 https 只会从"被浏览器拦掉"变成"连接失败"。正解是**相对路径** `/media/…` ——
它用当前页面的域名与协议，一份数据在本地 http 与线上 https 都对。

两层修法（都要，各管一半）：

```bash
# ① 数据层：找出并改写库里的绝对 http 媒体地址（先不带 --fix 看一眼）
python manage.py check_media_urls
python manage.py check_media_urls --fix

# ② 渲染层：前端已内置三层兜底（第 430 / 431 批）
#    · 富文本走 sanitizeRichText 时，<img src="http://…/media/…"> 会被改写成相对路径
#      （utils/richText.js 的 DOMPurify 钩子）
#    · 图片组件走 getImageUrl 时同样归一（utils/image.js）
#    · **响应拦截器**（api/http.js，第 431 批）：JSON 响应里所有 http 媒体地址
#      在进内存那一刻就归一 —— 页面里大量 `<img :src="news.image">` 是直接绑数据的，
#      逐组件去包既漏又不持久，所以在数据层收口（blob 下载跳过）
#    → 所以**不重新导入历史数据**也能不再裂图；数据层那步仍然要做，是为了
#      API 消费方（移动端 / RSS）与"不被任何前端渲染的正文"
```

> `check_media_urls` **不在**系统助手的只读命令白名单里：它带 `--fix`，
> 助手不该建议模型去改数据。要修就在服务器上由人执行。
>
> ⚠️ **第 432 批更正**：上面这套"数据里有绝对地址"的判断**不是**那次线上 6 张裂图的原因 ——
> 真正的原因见下面第 7 条（构建产物里写死了 `http://127.0.0.1:8000/api`）。
> 命令本身仍然有用（数据体检），但跑出来是 0 条很正常。

另：`chrome-extension://invalid/`、`content.js … detectPageLang` 这类日志来自**浏览器扩展**，
不在本仓库里，可以忽略。

### 7. 生产构建写死 `127.0.0.1:8000`（第 432 批，**这才是那次裂图的主因**）

排查结果：服务器上 `frontend/` 只有 `.env.development`，**没有 `.env.production`**。
`vite build` 取不到 `VITE_API_BASE_URL`，代码里五处兜底 `http://127.0.0.1:8000/api`
被原样打进产物：

```bash
grep -c "127.0.0.1:8000" dist/assets/index-*.js     # 修复前：3
```

于是线上：

| 现象 | 实际请求 |
|---|---|
| 图片裂开（Mixed Content，`host is an IP address`） | `http://127.0.0.1:8000/media/…` |
| 接口可能整片失败 | `http://127.0.0.1:8000/api/…`（打到**访客自己的机器**） |

> ⚠️ **更正上一版第 6 条的判断**：那次 6 张裂图的主因**不是**库里的脏数据，
> 而是构建产物里的这个兜底地址（`127.0.0.1` 本身就是 IP）。`check_media_urls`
> 仍然是有用的数据体检，但跑出来是 0 条也很正常。

修法（第 432 批，已入库）：

1. **兜底值改成同源 `/api`** —— "没配"时的行为必须是最安全的那个：
   `http.js` / `api/index.js` / `assistant.js` / `utils/axios.js` / `main.js` 五处；
2. 补上 **`frontend/.env.production`**（`VITE_API_BASE_URL=/api`，根 `.gitignore` 早已白名单放行）；
3. 媒体地址只拼 **origin**（去掉 `/api`，见 `utils/mediaUrl.js: mediaOrigin()`）——
   否则会拼成 `…/api/media/…`（404）。

**发布前必须验一条**（0 才算对）：

```bash
cd frontend && npm run build
grep -c "127.0.0.1:8000" dist/assets/*.js     # 期望：0
curl -I https://<域名>/media/<随便一个已存在的文件>   # 期望：200（nginx 的 location /media/）
```

顺带：`getThumbnailUrl` 原来用 `new URL(path, baseUrl)`，生产下 base 为空会抛
`Invalid URL` —— 已改成手工拼 query。

## 六、Docker 部署的实战坑（2026-11 实战复盘）

这一节全部来自一次真实的线上故障排查，**每条都花了时间**，按"症状 → 真因 → 处置"写。

### 1. 整站 `ERR_CONNECTION_REFUSED` / `curl` 返回 `000`

**真因**：`deploy/nginx.conf` 被覆盖成了仓库里的 **HTTP-only 样板**（88 行、只有 `listen 80`），
443 没人监听 → HTTPS 直接连不上。

```bash
grep -c 'listen 443' deploy/nginx.conf          # 必须是 ≥1
grep -c 'ssl_certificate ' deploy/nginx.conf    # 必须是 ≥1
```

**处置**：从备份或 stash 取回 HTTPS 版，验证后 `up -d --force-recreate nginx`。
**教训**：覆盖前先 `grep -c 'listen 443'`；`cp *.bak` 这种"按时间挑备份"最容易挑错版本。

### 2. nginx 反复 `Restarting`，日志 `cannot load certificate`

**真因**：`docker-compose.yml` 的 nginx 服务缺证书挂载（或 compose 被换成仓库版）：

```bash
docker compose config | grep -c 'published: "443"'      # 必须 ≥1
docker compose config | sed -n '/^  nginx:/,/^  [a-z]/p' | grep certs
```

**处置**：补 `- "443:443"` 与 `- ./deploy/certs:/etc/nginx/certs:ro`，再 `up -d --force-recreate nginx`。

### 3. `nginx -t` 报 `host not found in upstream "backend:8000"`

**这不是配置错误** —— 你在**一次性容器**里验证，它不在 compose 网络里，解析不到服务名。
正确的验证方式（网络 + 证书都要挂）：

```bash
sudo docker run --rm --network app_default \
  -v $PWD/deploy/nginx.conf:/etc/nginx/conf.d/default.conf:ro \
  -v $PWD/deploy/certs:/etc/nginx/certs:ro \
  nginx:1.27-alpine nginx -t
```

> 网络名不一定是 `app_default`，用 `sudo docker network ls | grep -i default` 确认。

### 4. backend 重建后接口全 `502`

**真因**：nginx 缓存了旧容器的 IP（`proxy_pass http://backend:8000` 在启动时解析一次）。
**处置**：固定顺序 —— **先 `up -d --build backend`，再 `restart nginx`**，并等后端 healthy。

### 5. 容器 `Restarting (134)`，日志只有两行

```
terminate called without an active exception
Aborted (core dumped)
```

**真因**：`ApiConfig.ready()` 起守护线程预热 YOLO/torch，而容器启动命令是
`python manage.py migrate && gunicorn …` —— `migrate` 是短命进程，退出时解释器强杀
还在跑 torch 的线程 → SIGABRT(134) → `&&` 断链 → gunicorn 永不启动。

**处置**：第 436 批已修（`_should_warm_up()`：只有 gunicorn 这类服务进程才预热）。
**退出码速查**：

| 退出码 | 含义 | 先看什么 |
|---|---|---|
| `1` | 应用报错 | `docker compose logs --tail 50 backend` |
| `134` | SIGABRT（native 库/线程） | `terminate called without an active exception` |
| `137` | OOM 被杀 | `docker stats`、模型加载内存（每个 worker 约 700MB） |

### 6. 浏览器一直跑旧 JS（明明 dist 是新的）

**真因**：入口壳 `index.html` 被缓存 / Service Worker 接管。表现极具迷惑性 ——
服务端 JS 里已经 `grep` 不到 `localhost:8000`，浏览器照样请求它。

**处置**：`deploy/nginx.conf` 里必须有这两段（第 43x 批加入）：

```nginx
location = /index.html { add_header Cache-Control "no-cache"; expires -1; }
location = /sw.js      { add_header Cache-Control "no-cache"; expires -1; }
```

验证：

```bash
curl -sI https://<域名>/ | grep -i cache-control     # 期望 no-cache
```

浏览器侧清一次：

```js
navigator.serviceWorker.getRegistrations().then(r => r.forEach(x => x.unregister()))
```
DevTools → Application → Storage → **Clear site data** → `Ctrl+Shift+R`。

### 7. 图片 404 / 路径里带 `%E2%80%A6`

`%E2%80%A6` 是省略号 `…` —— 从控制台**复制被截断的 URL**得到的假地址，不存在这个文件。
正确的取法：右键裂图 →「复制图片地址」，或 Network → Img → 点请求看 **Request URL**。

真实的媒体文件校验（不用浏览器）：

```bash
f=$(ls backend/media/detection_uploads | head -1)
curl -s -o /dev/null -w "图片:%{http_code}\n" "https://<域名>/media/detection_uploads/$f"
```

### 8. 每次 `git pull` 都被"本地部署适配"挡住

`backend/Dockerfile`（腾讯云镜像源）、`deploy/nginx.conf`、`docker-compose.yml`、
`deploy/schedule/*.bat` 是**每台机器专属**的改动，会一直脏着。

推荐做法：**把这几个文件在本地提交一次**（不推到 GitHub），之后 pull 就不会被挡：

```bash
git add backend/Dockerfile deploy/nginx.conf docker-compose.yml deploy/schedule/
git commit -m "chore(deploy): 本机部署适配"
```

不得已要临时绕过：

```bash
git -c rebase.autoStash=true pull --rebase origin main
# 若 autostash 回放冲突：改动仍在 stash 里，用
git checkout "stash@{0}" -- deploy/nginx.conf docker-compose.yml
git reset -q -- deploy/nginx.conf docker-compose.yml
```

> ⚠️ autostash 冲突后**工作区会退回仓库版**（HTTP-only 配置）—— 这时**别重启 nginx**，
> 先按上面恢复文件、`nginx -t` 通过后再重启。

### 9. 构建缓存吃满磁盘

```bash
sudo docker system df
sudo docker builder prune -f      # 一次能回收 10GB 量级
```
### 10. 重建容器时数据被"回退"（最隐蔽的一条）

**症状**：用户反馈"我刚上传的识别不见了"；`users/detections` 条数在每次 `docker compose up -d --build backend` 之后**少几条**。

**真因**（2026-11 实测）：

```yaml
# 修复前 docker-compose.yml 的 backend 卷
volumes:
  - ./backend/media:/app/media
  - ./backend/logs:/app/logs      # 只有这两个
```

Django 的 SQLite 默认落在 `/app/db.sqlite3`（**容器内**），而 Dockerfile 是 `COPY . .` ——
宿主机 `backend/db.sqlite3` 被**烤进镜像**。于是：

1. 重建镜像时，镜像里带的是"构建那一刻"的 DB 快照；
2. 新容器启动 → 数据回退到快照；
3. 构建之后新产生的记录随旧容器销毁。

实测数字：线上 `detections=141`，宿主机文件 140 —— 等于**已经吞掉 1 条**。

**修法**（第 438 批已入库）：

```yaml
volumes:
  - ./backend/media:/app/media
  - ./backend/logs:/app/logs
  - ./backend/db.sqlite3:/app/db.sqlite3   # ← 数据库落宿主机
  - ./backups:/backups                     # ← 备份产物也落宿主机
```

再加 `backend/.dockerignore` 排除 `db.sqlite3` / `media/` / `logs/` / `backups/` ——
否则镜像仍然是"生产数据快照"，只是运行时被挂载遮住而已。

**迁移步骤**（在已有数据的机器上，顺序不能错）：

```bash
cd /home/ubuntu/app
sudo docker compose stop backend
sudo docker cp app-backend-1:/app/db.sqlite3 ./backend/db.container.sqlite3
# 核对条数：容器里那份才是真实数据
python3 -c "import sqlite3;print(sqlite3.connect('backend/db.container.sqlite3').execute('select count(*) from api_detectionhistory').fetchone())"
sudo mv ./backend/db.container.sqlite3 ./backend/db.sqlite3
sudo chown ubuntu:ubuntu ./backend/db.sqlite3
mkdir -p backups
# 改 compose 加两个挂载后：
sudo docker compose up -d --force-recreate backend && sudo docker compose restart nginx
```

**验证**：`detections` 条数不变 → 再 `up -d --build backend` 一次 → 条数**仍然不变**，才算修好。

> 教训：**只要数据在容器可写层里，`--build` 就是一次隐形的数据回退**。
> 检查清单：`docker compose config | grep -A6 volumes` —— DB、media、logs、backups 四样都应在宿主机。
