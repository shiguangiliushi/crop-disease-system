# 部署与运维指南

> 第 94 批新增。此前项目里**没有任何生产启动方式**：全仓没有 Dockerfile、没有 gunicorn 配置、
> 没有 Nginx 配置，`requirements.txt` 只有 8 行且**照它装不出能跑的环境**。
> 这份文档把"从零到能访问"的每一步写清楚，并附上这一轮真实踩到的坑。

## 一、部署前先跑一次环境自检

```bash
cd backend
python manage.py check_env            # 人看的报告
python manage.py check_env --strict   # 有问题就退出码 1（可放进 CI）
```

它会检查六件事，**每一项都对应过一次真实事故**：

| 检查 | 为什么要有这一条 |
|---|---|
| 依赖包版本对照 `requirements.txt` | 那个文件曾经缺 `django-cors-headers` / `django-filter`，且版本与开发环境全不一样 |
| `INSTALLED_APPS` 里的第三方应用能否导入 | 同上 —— 装了才算数 |
| 数据库 / 缓存 / 迁移 / 模型文件 / 媒体目录可写 | "服务起来了但迁移没跑"是最常见的上线故障 |
| 生产开关（DEBUG / ALLOWED_HOSTS / HTTPS / 邮件后端） | 只提示不拦截：开发环境本来就该是 DEBUG=True |

## 二、环境变量

模板在 `backend/.env.example`，复制成 `backend/.env` 后按需填：

```bash
cp backend/.env.example backend/.env
# 生产至少填这三项：
#   DJANGO_DEBUG=False
#   DJANGO_SECRET_KEY=<50 位随机串>     ← 不填会**直接拒绝启动**（有意为之）
#   DJANGO_ALLOWED_HOSTS=example.com,10.0.0.5
python -c "from django.core.management.utils import get_random_secret_key as g; print(g())"
```

优先级：**真实环境变量 > `.env` 文件 > 代码里的开发默认值**。

### 生产相关的开关（第 94 批新增）

| 变量 | 默认 | 说明 |
|---|---|---|
| `DJANGO_SECURE_SSL_REDIRECT` | 生产 `True` | http 请求 301 到 https。**内网 http 部署要显式设 False**，否则无限重定向 |
| `DJANGO_SECURE_HSTS_SECONDS` | `0` | HSTS。默认关 —— 浏览器会记住 max-age，**确认 HTTPS 稳定后再开** |
| `DJANGO_COOKIE_SECURE` | 生产 `True` | 只在 HTTPS 下发会话/CSRF Cookie |
| `DJANGO_USE_X_FORWARDED_HOST/PORT` | 生产 `True` | 有反代时开；没有反代就别开（可被伪造） |
| `DJANGO_SERVE_MEDIA` | `= DEBUG` | 生产是否由 Django 托管 `/media/`。没配 Nginx 的小规模部署设 `True` |
| `DJANGO_WHITENOISE` | 生产 `True` | 静态文件（admin 样式）由 WhiteNoise 托管；没装这个包自动跳过 |
| `DJANGO_TOKEN_TTL_SECONDS` | `604800` | Token 有效期（秒）。**`0` = 不过期**（仅开发用） |

## 三、三种部署方式

### 方式 A：单机 + gunicorn（最小可用，推荐先跑通这个）

```bash
cd backend
pip install -r requirements.txt -r requirements-prod.txt

# 1) 准备环境
cp .env.example .env        # 填 DJANGO_SECRET_KEY / DJANGO_DEBUG=False / ALLOWED_HOSTS
#   内网 http 部署再补：DJANGO_SECURE_SSL_REDIRECT=False、DJANGO_COOKIE_SECURE=False

# 2) 建库与静态文件
python manage.py migrate
python manage.py collectstatic --noinput

# 3) 起服务（两个 worker；见 gunicorn.conf.py 里的调参说明）
gunicorn -c gunicorn.conf.py crop_disease_backend.wsgi:application

# 4) 验证
curl -i http://127.0.0.1:8000/api/health/          # 期望 200 {"status":"ok"}
curl -i "http://127.0.0.1:8000/api/health/?deep=true"   # 额外看迁移与模型
```

前端产物自己发（任选 Nginx / `python ../docs/tools/serve_spa.py` / 任意静态服务器），
反代 `/api`、`/media` 到 8000 即可。

### 方式 B：Docker Compose（后端 + Nginx + 两个前端）

```bash
# 1) 构建前端产物（Nginx 直接发 dist，不在容器里跑 node）
cd frontend && npm ci && npm run build-only && cd ..
cd mobile   && npm ci && npm run build      && cd ..

# 2) 准备后端环境变量
cp backend/.env.example backend/.env        # 至少填 DJANGO_SECRET_KEY

# 3) 起
docker compose up -d --build

# 4) 验证
curl -i http://localhost/api/health/
# 桌面端： http://localhost/
# 移动端： http://localhost/m/
```

`docker-compose.yml`、`backend/Dockerfile`、`deploy/nginx.conf` 都在仓库里。
数据库默认仍是 sqlite（挂卷持久化）；换 Postgres 的步骤写在 compose 文件末尾的注释里。

### 方式 C：只是个局域网演示

```bash
cd backend
python manage.py runserver 0.0.0.0:8000
```

够用，但要知道它的三个限制：单进程（并发请求会排队）、无超时保护、启动时打印"不要在生产使用"。

- [ ] 限流真的要生效：把缓存从 LocMem 换成 Redis/Memcached（见下）
- [ ] 邮件配 SMTP（否则找回密码的重置链接只会打进日志）
- [ ] `/api/health/` 接进监控；`/media` 与数据库有备份
- [ ] 上线前跑一次 `python manage.py check_env` —— **或直接看管理端「系统健康」页**
      （第 157 批：两者是同一套检查，页面还带数据量概览；仅全权管理员可见）
- [ ] **挂上备份定时任务**并做过一次恢复演练（见 [备份与恢复.md](备份与恢复.md)）：
      `backend_backup --keep 30 --quiet` 每天跑，`backup_verify --strict` 每天校验，
      `DJANGO_BACKUP_DIR` 指向另一块盘或网络存储
- [ ] **演练一次"能不能恢复"**（第 154 批固化成了命令）：
      `python manage.py backup_drill --yes` —— 造标记物 → 备份 → 破坏 → 恢复 → 逐项核对；
      实测 7/7 项通过。⚠️ 它会**改写数据库**，生产请用另一套数据跑（或 `--force` 并选维护窗口）。
      建议把它挂成**每月一次**（在预发/副本上），否则"有备份"只是信念。
- [ ] **挂上注销冷静期的到期任务**：`purge_deletion_requests` 每天跑
      （不跑的话用户以为账号已注销，个人信息却还在库里；`check_env` 会报警）
- [ ] **挂上 media 清理任务**（第 107 批补）：`prune_media --yes --min-age-days 7` 每天跑。
      **必须带 `--yes`**，否则只报告不删。不挂不会立刻出事，但 `media/` 会只增不减地长 ——
      第 106 批实测清出 791 个无引用文件 / 10.3 MB（占当时 media 的一半）。

### 定时任务一览（四件事，缺一件都会有"安静的故障"）

```cron
# 每天 03:00 备份，只留最近 30 份
0  3 * * *  cd /path/to/backend && /path/to/python manage.py backend_backup --keep 30 --quiet
# 每天 03:30 校验最新一份（有问题退出码非 0，接告警）
30 3 * * *  cd /path/to/backend && /path/to/python manage.py backup_verify --strict
# 每天 04:00 清理没有数据库引用的上传文件
0  4 * * *  cd /path/to/backend && /path/to/python manage.py prune_media --yes --min-age-days 7
# 每天 04:30 执行到期的注销申请（冷静期结束的账号）
30 4 * * *  cd /path/to/backend && /path/to/python manage.py purge_deletion_requests
```

| 任务 | 不挂的后果 | 为什么"安静" |
|---|---|---|
| `backend_backup` | 出事时没有可恢复的数据 | 平时完全无感 |
| `backup_verify` | 备份坏了也不知道，真恢复时才发现 | 同上 |
| `prune_media` | 磁盘只增不减 | 涨得慢，看不出异常 |
| `purge_deletion_requests` | 用户以为账号已注销，个人信息还在库里 | 用户不会回来告诉你 |

`manage.py check_env` 会检查**备份新鲜度**与**到期未执行的注销申请**并报警；
`prune_media` 没有"新鲜度"概念，所以它没法被自检发现 —— 只能靠上面这张表记住。

## 五、这一轮踩到的坑（都是"静默失败"型）

### 1. `django.conf.urls.static.static()` 在 `DEBUG=False` 下是**静默空操作**

```python
def static(prefix, view=serve, **kwargs):
    ...
    elif not settings.DEBUG or urlsplit(prefix).netloc:
        return []          # ← 生产下什么都不挂，且不报错
```

所以"用 `static()` 挂 `/media/` 到生产"是**配了等于没配** —— 页面表现是"图片全是碎的"，
而开发机上永远不会出现。正确做法是自己写 `re_path` 指向 `django.views.static.serve`：

```python
urlpatterns += [
    re_path(r'^%s(?P<path>.*)$' % re.escape(settings.MEDIA_URL.lstrip('/')),
            media_serve, {'document_root': settings.MEDIA_ROOT}),
]
```

（`serve` 自带 `safe_join`，实测 `/media/%2e%2e/db.sqlite3` 会被拦成 400。）

### 2. Token 过期"配了但不生效"

`TOKEN_EXPIRED_AFTER_SECONDS` 一直只有定义、**没有任何代码读它** ——
DRF 的 `TokenAuthentication` 不校验创建时间。所以"7 天过期"只是一句注释。
第 94 批在 `api/middleware.py` 里真正执行（过期即删、按未认证处理，带 `X-Token-Expired: 1`）。

**连带修掉一个更隐蔽的问题**：登录用的是 `Token.objects.get_or_create(user=...)`，
于是"过期但还没被用过"的 Token 会被原样返回 —— 用户密码输对了，拿到的却是失效凭证。
现在登录/注册一律 `delete()` + `create()`（顺带好处：登录即轮换，旧凭证立刻失效）。

### 3. 生产仍在用 LocMemCache

**限流计数器就存在缓存里** —— 多 worker 下每个进程各算一份，LocMem 会让限流形同虚设。
`check_env` 与 `/api/health/` 都会把这件事标出来（`degraded` / 提示语）。

第 153 批核对：缓存配置现在在 `settings.py` 有**五级优先级**
（`DJANGO_CACHE_URL` → `DJANGO_CACHE_BACKEND` → 测试用 LocMem →
`DEBUG=True` 用**文件缓存** `backend/cache/` → 生产才回落 LocMem 并 `warnings.warn`）。
所以**不用改代码**，设一个环境变量就行：

```bash
# .env / 部署环境里
DJANGO_CACHE_URL=redis://127.0.0.1:6379/1
```

```python
# 想显式指定后端也可以（等价于 DJANGO_CACHE_BACKEND）
# settings.py 会把它拼成 CACHES['default']，无需手写整个字典
```

> ⚠️ 开发环境（`DEBUG=True`）用的是**文件缓存**（`backend/cache/`），不是 LocMem ——
> 这样 `runserver --noreload` 重启进程也不会把限流计数清零。

### 4. Nginx 默认 `client_max_body_size 1m`

识别图允许 5MB —— 不改 Nginx 的话上传会在**反代层**就被 413 拒掉，
而且前端看不到 Django 的任何提示（`deploy/nginx.conf` 里已设成 12m）。
