## 一、现状：它为什么"没怎么用到"

| 证据 | 位置 |
|---|---|
| 模型里有这个取值 | `backend/api/models.py:38` `('EDITOR', 'Information Editor')`，默认值是 `USER` |
| 后台只是**展示 + 筛选** | `AdminUsersView.vue:71`（筛选下拉）、`:765` 角色标签映射 |
| **没有任何权限判定读它** | `permissions.py:21-24`、`views_user.py:968-972`、`auth.js:145-158` 全部是 `is_staff or is_superuser or role == 'ADMIN'` |
| **界面刻意不提供"改角色"** | `views_user.py:691-695`（第 95 批的决定：改角色属提权，走 Django admin） |
| 库里 0 个用户 | `ADMIN=2`（admin/audit）、`USER=3`、`EDITOR=0` |

结论：它是一个**没有接线的标签**。要让它有用，缺的不是"下拉里多一项"，而是**一整套能力口径**。

## 二、动手前必须先解决的事：口径被复制在约 30 处

> ⚠️ **本节的行号引用在第 124 批之后已全部失效**（口径已收口到 `capabilities.py`，
> 本节描述的"每模块各写一份 `_is_admin`"是**改动前**的状态）。保留它只为说明**当时为什么要先收敛口径**，
> 不要照着这里的行号去改代码。

后端目前有三种"管理员"写法**同时存在**，而且它们**并不等价**：

| 写法 | 语义 | 出现处（模块） |
|---|---|---|
| `permission_classes = [IsAdminUser]`（DRF 自带） | **只认 `is_staff`** | `views.py` FeedbackView、`views_forum.py` ForumBoardViewSet、`views_sensitive.py`、`views_user.py` 的 UserList/AdminUserList/AdminUserDetail/AdminUserResetLink |
| `IsAdminOrReadOnly` | `is_staff` / `is_superuser` / `role='ADMIN'` | `permissions.py:21`（病害百科写权限） |
| **每个模块各写一份**同样的判定（有的叫 `_is_admin(user)`，有的是内联表达式） | 同上 | `news_views.py`、`views.py`（Statistics / DetectionHistory / Clear / Report）、`views_alert.py`、`views_calendar.py`、`views_dashboard.py:45`、`views_expert.py`、`views_forum.py`、`views_notify.py`、`views_pest_import.py`、`views_pest_types.py`、`views_report.py`、`views_user.py`（UserProfileView / AdminUserDetail） |

> 具体形态例如 `views_dashboard.py:45`：
> ```python
> def _is_admin(user):
>     """与项目其它管理端一致的管理员判定（第 17 批统一口径）"""
>     return bool(user and user.is_authenticated
>                 and (user.is_staff or user.is_superuser or getattr(user, 'role', None) == 'ADMIN'))
> ```
> 注释说"统一口径"，但**实现是每模块一份拷贝** —— 改一处不会影响别处。

两个已经存在的**不一致**（本轮盘点新发现，不是 EDITOR 带来的）：

1. `role='ADMIN'` 但 `is_staff=False` 的用户，**能**写病害百科、**不能**用用户管理接口
   （因为那里用的是 DRF 的 `IsAdminUser`）；
2. 反过来 `is_staff=True` 但 `role='USER'` 的人，两边都能用。

> 如果在这种状态下直接给 EDITOR 开口子，就得在 30 个地方各判断一次，
> 必然出现"这个接口放行了、那个接口忘了"——第 106 批的教训就是这个：
> *注释只写在一处，另一个方法照旧错着*（见 `views.py` 的 `PestTypesView` 注释）。
> 所以第一批活必须是**收敛口径**，而不是直接改权限。

## 三、建议的能力矩阵（产品口径）

把"管理员"拆成三个能力，EDITOR 只拿第一个：

| 能力 | 含义 | ADMIN / 超管 | **EDITOR** | USER |
|---|---|---|---|---|
| `CONTENT_MANAGE` | 维护内容与处理内容事务 | ✅ | ✅ | ❌ |
| `USER_ADMIN` | 用户账号、专家身份、他人识别记录 | ✅ | ❌ | ❌ |
| `BROADCAST` | 对全体用户发声、系统级开关 | ✅ | ❌ | ❌ |

逐项落到现在的功能上（**具体接口清单在实现时以本表逐条落表，不要凭记忆挑接口**）：

### `CONTENT_MANAGE` —— EDITOR 可以做

- 病害百科：新增 / 修改 / 删除 / 批量导入（`PestEncyclopediaViewSet` 写、`views_pest_import`）
- 新闻：新增 / 修改 / 删除 / 上下架（`news_views.NewsViewSet` 写）
- 内容审核：`GET /api/forums/posts/?status=pending`（待审列表）、
  `POST /api/forums/posts/<id>/approve/`、`POST /api/forums/posts/<id>/reject/`、
  `POST /api/forums/posts/bulk-review/`（批量，第 100 批）
- 意见反馈：查看全部、回复（`FeedbackView` 的管理员分支）——**删除建议留给 ADMIN**
- 种植日历：农事任务的增删改（`views_calendar` 的写接口）
- 只读：数据看板、审核列表

### `USER_ADMIN` —— EDITOR 不能碰

- `/api/admin/users/`（列表 / 详情 / 软删除 / 批量删除）
- `/api/admin/users/<id>/reset-link/`（签发密码重置链接）
- 专家授予 / 取消（`views_expert`）
- 识别记录"全部用户"视图 + 清空（`DetectionHistoryView` 的 `all_users` 分支、`DetectionHistoryClearView`）
- 用户维度的统计 / 导出（`views_report`、`views_dashboard` 里涉及具体用户的部分）

### `BROADCAST` —— EDITOR 不能碰

- 系统公告：发布 / 修改 / 删除（`AnnouncementViewSet`）
- 预警推送（`views_alert` 的 push）
- 敏感词管理（`views_sensitive`）
- 论坛版块管理（`ForumBoardViewSet` 写）
- 反馈数据集统计 / 导出（`AdminFeedbackDatasetStatsView`）

### 后台界面（侧栏）随之变化

| 侧栏项 | ADMIN | EDITOR |
|---|---|---|
| 数据看板 | ✅ | ✅（只读） |
| 内容审核 | ✅ | ✅ |
| 新闻管理 | ✅ | ✅ |
| 病害百科维护 | ✅ | ✅ |
| 意见反馈 | ✅ | ✅（不含删除） |
| 用户管理 | ✅ | **❌ 菜单不显示 + 直接输网址被弹回 + 接口 403** |

> 三处必须同时做：**菜单隐藏**只是体验，**路由守卫**防手输网址，**后端权限**才是真边界。

## 四、分四批实施（每批都能独立验证、独立回滚）

### 第 124 批：把口径收敛成一处（**行为完全不变**）

- 新增 `backend/api/capabilities.py`：
  - `CAP_CONTENT / CAP_USER_ADMIN / CAP_BROADCAST`
  - `has_capability(user, cap)`：`is_superuser` → 全部；`is_staff` 或 `role=='ADMIN'` → 全部（**保持今天的行为**）；`role=='EDITOR'` → 仅 `CONTENT`（本批先不生效，用常量开关控制）；
  - DRF 权限类 `HasCapability`（`permission_classes = [HasCapability.of(CAP_CONTENT)]` 形式）。
- 把 30 处内联判定**逐处替换**为能力判定，**先保持结果一致**。
- 前端：`authStore.isAdmin` 拆成 `canAccessConsole` + `capabilities`（同样先保持行为不变）。
- **验证**：现有后端 508 条测试全绿（这是"没改行为"的证明）+ 前端 82 单测 + 三个浏览器脚本。
- 产出：一份**接口 × 能力对照表**（实现时逐条填，作为后面几批的依据）。

### 第 125 批：EDITOR 的权限真正生效（后端）

- 打开开关：`role=='EDITOR'` → `CAP_CONTENT`。
- **补一类新测试**：`role × 端点` 的矩阵测试（ADMIN 全通、EDITOR 只能过 CONTENT、USER 全 403），
  把上面那份对照表逐行断言 —— 这样以后再漂移会被测试抓住，而不是靠人记。
- 顺带修第二节那两个**已存在的不一致**（统一成"能力口径"，并明确 `is_staff` 仍是全权管理员，
  因为 Django admin 靠它）。

### 第 126 批：后台界面按能力显示（前端）

- 侧栏项带 `capability` 字段并按能力过滤；路由 meta 从 `requiresAdmin` 升级为 `requiresCapability`。
- 页面内按钮按能力隐藏：删除用户 / 签发重置链接 / 发布公告 / 删除反馈 等。
- `AdminLayout` 顶部身份标签：EDITOR 显示「信息编辑员」（现在只有 管理员/普通用户 两种）。
- **验证**：E2E 用 EDITOR 账号登录 → 侧栏 5 项（无用户管理）、手输 `/admin/users` 被弹回、
  直接 `curl` 用户管理接口 403；再用 ADMIN 账号跑一遍既有 42 项断言确认没退化。

### 第 127 批：角色赋值与护栏

- 「用户管理」行内加「改角色」（仅 `is_superuser` 可操作）：
  - **不能给"权限不低于自己"的账号改角色**（复用第 120 批签发重置链接那套护栏思路）；
  - 不能把别人升成 `ADMIN`（要升只能走 Django admin）——只允许在 `EDITOR` / `USER` 之间调；
  - 写审计日志（谁、什么时候、把谁从什么改成什么）。
- 用户管理列表的角色筛选保持可用；角色标签颜色沿用（EDITOR = 橙色 warning）。
- 或者**只做显示不做赋值**：如果暂时不想在 Console 里开提权入口，就在筛选下拉里注明
  「信息编辑员（未启用）」并保持走 Django admin —— 那就只需第 126 批，成本减半。

## 五、必须守住的风险点

1. **前端隐藏 ≠ 权限**：EDITOR 的隔离必须由后端保证；E2E 里一定要有"直连接口 403"的断言。
2. **`is_staff` 的语义不能动**：Django admin（`/admin/`）靠它进门，改成"按能力"会让
   现有超管进不去自带后台。建议明确写成：`is_staff or is_superuser or role='ADMIN'` = 全权，
   `role='EDITOR'` = 内容能力。
3. **Token 里的 `role`**：登录响应与 `/api/check-auth/` 都已返回 `role`，前端据此算能力即可；
   但**改了角色之后**，已登录的浏览器仍旧按旧角色显示菜单（要等下一次登录/刷新）。
   建议：改角色成功后提示"对方需重新登录生效"，并在文档里写清这一点（不要试图热更新对方会话）。
4. **提权口径**：任何"改角色"都必须禁止"给自己或权限≥自己的人升权"，否则 EDITOR 能把自己变成 ADMIN。
5. **移动端**：`/api/pest-types/`、识别记录等接口若也在移动端用，能力口径变更后要一起回归
   （移动端仓库不在本目录，改动前先确认调用面）。
6. **回归基线**：后端 508 条测试是"行为没变"的唯一凭证，第 124 批必须全绿才算收敛成功。

## 六、备选方案 B：改用 Django 权限位（`auth.Permission` + 用户组）

- 优点：标准、可扩展、Django admin 里也能复用同一套权限、以后加能力不用改代码。
- 代价：项目现在的口径是 `role + is_staff`，且**移动端/前端多个地方**都按它判断；
  改权限位等于把"谁能做什么"整体迁到 `ModelBackend` 体系，要动认证、序列化（要返回权限列表）、
  前端能力计算，以及 Django admin 的超级用户语义。
- 建议：**现在不做**。等到能力超过 3-4 个、或者要按"模块 × 动作"细分（例如只读审核员、
  只改百科的编辑）时再迁。当前的 `capabilities.py` 设计已经把这层抽象出来了，
  将来替换实现即可，调用方不用改。

## 七、需要你拍板的四个产品决策

| # | 问题 | 我的建议 |
