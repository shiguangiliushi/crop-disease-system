# 提交与仓库约定

> 这份文档回答三个问题：**怎么拆提交、什么不该入库、提交前查什么**。
>
> 起因（第 136 批的一次目录检查）：71 个文件的行尾不是 LF（`.gitattributes` 早已约定 LF）、
> 一个 0 字节的沙箱探针空文件被首次提交一起纳入了仓库；而我为第 115~135 批整理提交时，
> **按批拆分连续踩了两次坑**（见第三节）。把结论写下来，免得下次再踩。

## 一、提交信息格式

沿用既有风格，一条功能提交配一条文档提交：

```
<type>(<scope>): 中文描述

- 逐条列出"为什么这么改"，而不是"改了哪些文件"
- 涉及取舍时写清被否决的方案

验证：<跑过的命令与结果>
```

| type | 用途 |
|---|---|
| `feat` | 新功能 / 新页面 / 新接口 |
| `fix` | 修 bug（写明**触发条件**，例如"两个 runserver 抢日志锁"） |
| `docs` | 文档，尤其是 `docs: 记录第 N 批（<一句话>）` |
| `chore` | 工具、依赖、仓库卫生 |
| `refactor` / `test` | 不改行为的重构 / 只加测试 |

历史示例（可直接照抄句式）：

```
feat(私信): 重做客户端私信 —— 翻历史 / 已读回执 / 自动刷新 / 图片 / 删除会话
fix(router): 修掉 3 处无效的路由名（点了没反应），并加对账测试
docs: 记录第 114 批（重做客户端私信）
```

**约定**：动完代码就补一条 `docs:` 提交把这一批写进 `docs/系统完善记录.md` ——
每批都记「为什么 / 验证数据 / 下一步」，否则过两周没人说得清当时为什么这么改。

## 二、怎么拆提交：**按层，不按批**

单个文件常常横跨好几批（`router/index.js`、`i18n/messages.js`、`stores/auth.js`、`App.vue`
几乎每批都动）。**按批拆必须做 hunk 级手术**，容易拆错、收益又低；按层拆则每个提交
都有独立的验证依据：

| 顺序 | 提交 | 内容 | 验证依据 |
|---|---|---|---|
| ① | `feat(...): …后端` | `backend/`（含迁移） | `manage.py test api.tests` |
| ② | `feat(前端): …` | `frontend/src`、`frontend/package.json` | 单测 + `vue-tsc` + 构建 + 端到端脚本 |
| ③ | `chore(工具): …` | `frontend/scripts`、`docs/tools` | 脚本自身可跑（有问题即退出码 1） |
| ④ | `docs: …` | `docs/`、`.gitignore`、仓库卫生 | 行尾/BOM 检查 |

## 三、具体做法（确定性写法）与三个坑

```powershell
# 需要重排已有提交时：回到基线，**保留全部改动**
git reset --soft <base-commit>
git reset -q                      # 清空暂存区（工作区不动）

# 逐组提交：用 git add -A 分组，commit **不跟 pathspec**
git add -A -- backend/api backend/crop_disease_backend
git commit -F .git\COMMIT_MSG_1.txt

git add -A -- frontend/src frontend/package.json ":(exclude)frontend/src/components/.dsh-write-probe.tmp"
git commit -F .git\COMMIT_MSG_2.txt
```

> **坑 1：`git commit -- <paths>` 会连带索引里其它已暂存内容一起提交。**
> 它只把**列出的路径**换成工作区版本，其余路径取索引 —— 于是"已经 staged 的删除/改动"
> 会跟着跑进这个提交（`dsh-write-probe.tmp` 的删除因此连续两次跑进"后端"提交）。
>
> **坑 2：`git add -A -- <目录>` 会把目录下**所有**改动一起收进来。**
> 探针文件就在 `frontend/src/components/` 下，所以它被"前端"提交自然收走；
> 要把它留给"文档与卫生"提交，必须用 `':(exclude)<path>'` 显式排除。
>
> **坑 3：中文提交信息别用 `-m`。**
> 在 Windows PowerShell 里直接 `git commit -m "中文…"` 有编码风险（仓库历史里出现过乱码前缀）。
> 用 `git commit -F <UTF-8 文件>`，提交完把消息文件删掉。

**删除文件**要用 `git add -A -- <path>`（或 `git rm`）—— 不带 `-A` 的 `git add` 对
"工作区已不存在的路径"会报 `did not match any file(s) of known to git`。

## 三点五、每批做完就推（第 151 批补）

简历上挂的是这个仓库的链接，所以**约定：每批记录提交完就推一次**，让远端始终等于本地最新：

```powershell
python docs/tools/push_and_verify.py          # 推送 + 核对（推荐）
python docs/tools/push_and_verify.py --proxy auto   # 网络被阻断时，自动用本机代理
```

三条注意事项：

1. **推送结论必须以「远端 ref」为准，不能以「命令没报错」为准**：
   `git push` 成功和失败**都会**在 PowerShell 里打出 `NativeCommandError`（git 的进度输出走 stderr），
   光看屏幕分不出来。第 152 批我就因此写过一句"✅ 已同步"，而那次推送其实**根本没成功**
   （`github.com:443` 连不上）—— 典型的假绿灯。
   现在用 `docs/tools/push_and_verify.py`：推完拿 `git ls-remote` 的 ref 与本地 `HEAD` **比一次**，
   不相等（或读不到远端）就以退出码 1 如实报告"这 N 个提交仍在本地"，并给出可选路径
   （开代理重跑 `--proxy auto` / 稍后重试 / 配 SSH key 走 22 端口）。
   手工核对也可以：`git rev-parse HEAD` 与 `git ls-remote origin main` 打出的哈希必须一致。
2. **推送前先跑第五节的四项自检**，尤其是"别把敏感文件或大文件带进提交" ——
   这是公开仓库，`backups/`、`backend/db.sqlite3`、`backend/logs/` 里都有真实用户数据。
   已入库的大文件（`backend/static/fonts/simsun.ttc` 17MB、`yolov8n.pt` 6MB、
   `api/newmodels/*.pt` 各 6MB）都在 GitHub 单文件 100MB 限制内，**不要**再往里加更大的。
3. **暂存用显式路径，不要 `git add .`**：这个仓库经常是"我和别人同时在改"
   （第 142 批就发生过：对方把自己的一批提交了，而我的 `git add -A -- <目录>` 差点把他
   没提交干净的改动一起收走）。显式路径 + `git commit -F <消息文件>` 多打几个字，
   换来的是"每个提交都是我打算提交的那些文件"。

> 第 152 批实测的网络情况（供下次排查参考）：DNS 能解析 github.com，但
> `github.com:443` **TCP 连不上**（推送失败）；而 `github.com:22`、`ssh.github.com:443`、
> `codeload.github.com:443`、`api.github.com:443` 都通。也就是说 ——
> **HTTPS 推送被卡住时，SSH（22 端口）往往是通的**，配一把 SSH key 是比反复重试更稳的解法。


## 四、什么不该入库

已确认被忽略（改动 `.gitignore` 后请用 `git check-ignore -v <path>` 复核）：

| 项 | 原因 |
|---|---|
| `venv/`、`backend/venv/`、`node_modules/` | 环境，体积大且平台相关 |
| `frontend/dist/`、`backend/staticfiles/` | 构建产物，`collectstatic` 可重建 |
| `backend/logs/` | 调试日志（曾涨到 20 MB+） |
| `frontend/dsh-shots/` | 界面取证截图（几十 MB） |
| `backups/` | 整个数据库副本 + 上传文件，含真实用户数据与口令哈希 |
| `backend/db.sqlite3` | 含真实用户表 |
| `.dsh-*`、`*.dsh-tmp` | **工具产生的探针/临时文件**（第 136 批补：一个 0 字节探针文件曾被提交进仓库） |

有意**不**忽略的：`backend/media/`（用户上传与示例图片）、`frontend/public/`（PWA 图标与 manifest）。

## 五、提交前自检

```powershell
# 1) 行尾：本仓库一律 LF（.bat/.cmd 例外）
python docs/tools/check_line_endings.py

# 2) BOM：Windows 上 Set-Content/Out-File 容易写进 BOM，会让 Python 源码解析失败
python docs/tools/strip_bom.py --check backend/api backend/crop_disease_backend frontend/src docs

# 3) 前端三条检查（英文语言包残留中文 / 术语一致性 / Element Plus 组件注册）
cd frontend; npm run check

# 4) 别把敏感文件或大文件带进提交
git status --porcelain | Select-String '\.env|secret|credential|\.sqlite3'
git status --porcelain | ForEach-Object { $_.Substring(3) } | Where-Object { (Test-Path $_) -and (Get-Item $_).Length -gt 1MB }
```

## 六、写文件的注意事项（踩过的坑）

- **不要用 PowerShell 的 `Set-Content` / `Out-File` 改源码**：它会写 BOM、并且**失败时把文件截断成 0 字节**
  （本项目因此丢过 `frontend/src/i18n/messages.js` 与 `AdminUsersView.vue`，靠 `docs/tools/restore_source_from_sourcemap.cjs`
  从生产构建的 sourcemap 才还原回来）；
- **Python 的 `Path.write_text()` 也要显式写 `newline='\n'`**（第 152 批补）：
  在 Windows 上它默认按平台换行翻译，`\n` 会被写成 `\r\n` —— 第 152 批我用一个 Python
  补丁脚本改了 7 个后端文件，全部变成 CRLF，提交前靠 `check_line_endings.py` 才发现。
  正确写法：`p.write_text(text, encoding='utf-8', newline='\n')`（Python 3.10+ 支持该参数）。
- 行尾：这类写入默认是 **CRLF**，与 `.gitattributes` 的 `eol=lf` 冲突，写完用 `check_line_endings.py` 过一眼；
- 用编辑工具或 `node -e`/Python 脚本改文件，改完**顺手跑一次**上面的自检。
