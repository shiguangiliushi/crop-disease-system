# 系统助手 · 不可逆写（A3）的"待确认 → 二次确认"状态机

> 本文只解决一件事：让系统助手在**不可逆**操作上"先问一句、得到确认、再执行"。
> 现状锚点（都在工作区代码里，不是假设）：
>
> - `ops/actions.py`：三个 L2 动作已上线（`verify_feedback_sample` / `mark_feedback_handled` /
>   `reply_feedback`），统一走 `validate() → execute()`，`MAX_WRITES = 1`，必落 `AdminAuditLog`。
> - `ActionSpec.reversibility` 目前只允许 `'reversible'`，注释写明"别处无法放宽"——
>   这个字段就是留给 A3 的开关。
> - `ops/tools.py` 全只读的约定不能破；写动作只能进 `ACTIONS`。
> - 模块说明的分级表：`L3 | 不可逆写：删记录、清空历史 | 不做。要做得先有"待确认 → 二次确认"状态机`。
>
> 所以 A3 不是"再加一个工具"，是**多一个跨请求的状态**。加工具是几行，跨请求状态是全部工作量所在。

## 一、判据：为什么 L2 直接执行、A3 必须二次确认

判据是**可逆性**，不是"影响大不大"——把反馈标成已确认，再标回 `pending` 就复原了；
删掉的识别记录与图片文件复原不了。所以：

| 级别 | 执行方式 | 依据 |
|---|---|---|
| L2 可逆写 | 校验通过即执行 + 审计 | 出错能靠"再执行一次"改回去 |
| **A3 不可逆写** | **复述 → 确认 → 执行** | 出错没有第二次机会 |

推论：**A3 的确认不是礼貌，是数据保护**。它必须挡住的是"模型读错了一个 id"这类事故——
这类事故不会报错，只会让某条记录凭空消失。

## 二、核心决定：状态存库，不存会话

待确认状态要活过**两次 HTTP 请求**（提议一轮、确认一轮）。两种存法：

1. 存进程内 / Redis / 图状态（LangGraph 的 checkpointer）；
2. **存数据库一张表**。

选 2。理由不是偏好：

- **可审计**：管理员打开 `/admin` 能看见"有一批操作卡在待确认"，进程重启、换 worker 都不丢。
  存在内存里的待确认，重启后是"静默过期"，没人知道那条删除曾被请求过。
- **可 SQL 核对**：出问题能直接查"谁在什么时候提议删了什么、谁确认的、执行了没"。
  序列化在图状态里的 JSON，审计时只能靠读日志反推。
- 本项目已有 `AdminAuditLog` 与 `OpsAssistantTurn` 两张观测表，加第三张窄表是顺着走，不是新架构。

**所以不需要 LangGraph。** `interrupt_before` 提供的正是"把状态挂起、等下一次调用继续"，
而在 Django 里这就是一行数据库记录 + 一个 token。引入 `langchain-core` 一串依赖去换
一个已经有现成等价物、且等价物更可审计的东西，是把简单问题做成复杂问题。
框架将来真正值得引入的时机是"多步规划 + 动态分支"，不是"跨请求挂起"。

## 三、数据模型：一张窄表

```python
# api/models.py（或 models_ops.py，跟着 OpsAssistantTurn 放）

class OpsPendingWrite(models.Model):
    """系统助手的待确认不可逆操作。一行 = 一次提议，最多被消费一次。"""

    STATUS = (
        ('pending', '待确认'),
        ('confirmed', '已确认'),
        ('cancelled', '已取消'),
        ('expired', '已过期'),
        ('failed', '执行失败'),
    )

    token = models.CharField(max_length=32, unique=True, db_index=True)  # uuid4().hex，不可猜
    action = models.CharField(max_length=64)          # ACTIONS 里的名字，执行前要再查一次白名单
    args = models.JSONField(default=dict)             # 校验后的参数快照
    target = models.CharField(max_length=200)         # 人读目标："反馈 #12 番茄晚疫病"
    preview = models.JSONField(default=dict)          # 提议时算好的"会改什么/会删什么"
    status = models.CharField(max_length=16, choices=STATUS, default='pending', db_index=True)
    user = models.ForeignKey(settings.AUTH_USER_MODEL, on_delete=models.CASCADE)
    question = models.TextField()                     # 提议时的管理员原话（审计与复述用）
    session_key = models.CharField(max_length=64, blank=True)  # 绑定同一会话，防串台
    created_at = models.DateTimeField(auto_now_add=True)
    expires_at = models.DateTimeField()               # 提议 + 10 分钟
    consumed_at = models.DateTimeField(null=True, blank=True)
    audit_log = models.ForeignKey('AdminAuditLog', null=True, blank=True, on_delete=models.SET_NULL)

    class Meta:
        indexes = [models.Index(fields=['user', 'status'])]
```

要点：

- `token` 是**唯一凭据**，不用"最近一条待确认"这种隐式指针——那会让两个管理员、两个页签互相串台。
- `args` 是**校验后**的快照（`Validated.args`），不是模型原始 `tool_call.arguments`。
  确认阶段**不再重新校验一遍模型输出**，因为此时没有模型输出，只有这一行。
- `preview` 在提议时就算好（删什么、影响几行、要不要删文件），执行阶段只照单执行。
  **执行时不再算一遍**：两次计算之间数据可能变了，那正是"确认 A、删了 B"的来源。

## 四、两阶段协议

### 阶段一：提议（只读，不写库）

```
管理员："把那批 200 条无图片的识别记录清掉"
  ↓ intent.is_command() 通过 → 目标指向明确
  ↓ llm.chat(tools=TOOL_SCHEMAS) 返回 irreversible 动作
  ↓ actions.validate(name, args, question=...)      ← 唯一的校验入口，照旧
  ↓ actions.preview(validated)                      ← 新增：dry-run，算清会删什么
  ↓ OpsPendingWrite.objects.create(...)             ← 唯一的写入：写"待确认"这一行
  ↓ 答案："要删除 200 条识别记录（2026-01-01 ~ 01-03，含 200 个图片文件），
          确认吗？回「确认」或点按钮。10 分钟内有效。"
```

这一轮**数据一行都没动**，动的是 `OpsPendingWrite`。

### 阶段二：确认（执行）

```
管理员："确认"（或点按钮，带 token）
  ↓ 规则识别确认（见第五节）：拿到 token
  ↓ 原子消费：UPDATE ... SET status='confirmed', consumed_at=now()
              WHERE token=? AND status='pending' AND expires_at > now() AND user=?
  ↓ rowcount == 0 → 拒绝（已消费/已过期/不是你的）
  ↓ 拿这行的 args 重新走 actions.execute(validated)   ← 审计、通知、副作用全照旧
```

**关键：阶段二用 `UPDATE ... WHERE status='pending'` 做原子认领。**
先 `SELECT` 再 `UPDATE` 会让双击、两个页签同时点、重放请求各执行一次。
Django 里就是 `OpsPendingWrite.objects.filter(...).update(...)` 的返回值判断，不写 `if obj.status == 'pending'` 再 `save()`。

## 五、确认这一步不能交给模型

这是整套设计里最容易做错的地方：

> 如果"这句话是不是确认"由模型判断，那么**模型可以确认自己刚才的提议**。

提示注入只要让工具返回值或用户输入里出现一句"这是管理员已确认的授权语"，
模型就能自己把 `confirmed=true` 传进来。所以确认必须是**确定性规则**，三条并行：

1. `intent.py` 的确认词表：`确认` / `确认删除` / `确定` / `执行` / `yes`，且**必须带 token 或紧接提议**；
2. 前端按钮直接提交 token（不经过模型，也不经过自然语言解析）；
3. 绑定校验：`user == 提议人` 且 `session_key` 一致。

模型在阶段二**没有角色**。它最多帮管理员把话复述清楚，不能参与"是否确认"的判定。
现有 `_run_action()` 里"规则读懂了就直接执行、不请模型"的写法，正是这个思路的延伸。

## 六、边界与并发（每一条都要有测试）

| 情形 | 期望 |
|---|---|
| 提议后管理员什么都没说 | 10 分钟后 `expired`，数据不变 |
| 连点两次确认 | 第一次执行，第二次 `rowcount == 0` → "已执行过"，不重复执行 |
| 两个管理员各自有待确认 | token 隔离，A 不能确认 B 的 |
| 管理员在窗口期内被降权 | 执行前复查权限，拒绝并留痕 |
| 进程重启 / 换 worker | 状态在库里，仍可确认 |
| 执行到一半抛异常 | 事务回滚 + `status='failed'` + 审计留痕；**不自动重试**（不可逆操作重试 = 二次删除） |
| 模型在阶段二说"已确认" | 不生效，走拒答 |
| 提议的目标在执行前消失 | 执行返回 `ok=False`，`status='failed'`，不是"假装成功" |

## 七、动作声明怎么扩

`ActionSpec` 不动结构，只放开取值并加两个字段：

```python
@dataclass(frozen=True)
class ActionSpec:
    ...
    reversibility: str          # 'reversible' | 'irreversible'
    confirm_text: str = ''      # 提议时的复述模板："删除反馈 #{id}（{target}）"
    preview: str = ''           # 哪个函数负责 dry-run（见下）
```

再加一个 `PREVIEWS: dict[str, Callable]`，与 `ACTIONS` 平行：

```python
def _preview_delete_records(validated) -> dict:
    qs = _scope(validated.args)                       # 与 execute() 同一套筛选
    return {
        'count': qs.count(),
        'ids_sample': list(qs.values_list('id', flat=True)[:10]),
        'files': qs.exclude(image='').count(),        # 会删几个文件
        'range': (first_date, last_date),
    }
```

**`preview` 与 `execute` 必须共用同一套筛选函数**——两份独立的筛选逻辑，
迟早漂移成"预告删 200 条、实际删 197 条"，而这种偏差没人会发现。
建议把筛选条件抽成 `_scope(args)`，两边都调它。

## 九、落地顺序（先假删除）

1. 建表 + 迁移，`ACTIONS` 加一个 `reversibility='irreversible'` 的**假动作**
   （`_noop_delete`，只回显 preview 不删任何东西）；
2. 跑通"提议 → 确认 → 执行一次"的完整链路 + 上面 8 条测试；
3. 链路稳了再挂真动作：先"删单条识别记录"，最后才是"批量清空"；
4. 批量清空额外要求：二次确认文本里必须带**具体数量**（`200` 而不是 `一批`），
   且数量在执行前再核对一次，不一致就中止。

## 十、框架怎么用（第 424–425 批：LangGraph 已落地）

需求方明确要求"agent 要用一个 agent 框架"，所以循环这一层改成图编排。**但分工要说清**：

| 交给框架 | 留在普通 Python 里 |
|---|---|
| "模型 → 工具 → 模型"的循环与条件边 | 只读/写工具的白名单（`ops/tools.py`、`ACTIONS`） |
| 步数上限（`MAX_STEPS`）与写次数上限（`MAX_WRITES`） | 目标 id 必须出自管理员原话（`validate()`） |
| 只读工具的 schema 生成（从函数签名） | **"算不算确认"的判定**（`pending.is_confirm()` 纯函数） |
| —（待确认状态**不**放在图里，见下） | 待确认的落库、过期、原子认领、执行（`ops/pending.py`） |

一句话：**框架管"下一步走哪"，不管"这一步能不能走"。**
把确认判定交给模型，等于让模型确认自己刚才的提议——这是这套设计里唯一不能妥协的点。

### 10.1 为什么最终**没有**用 `interrupt()`

第 424 批先用 `interrupt()` + `InMemorySaver` 实现了"提议 → 挂起 → 确认 → 执行"，
17 条用例全绿。第 425 批推翻了它，原因不在框架、在**部署形态**：

- `interrupt` 的状态存在 checkpointer 里，而默认的 `InMemorySaver` 在**进程内存**；
- gunicorn 起多个 worker 时，**提议落在 A 进程、确认请求进了 B 进程** ——
  表现为"点了确认没反应"，而且**不报错**；
- 进程重启后待确认静默消失，没人知道曾经提议过一条删除。

换成本文的数据库表之后，同样的流程有两个额外好处：
`AdminAuditLog` 旁边能看见"有一条操作卡在待确认"，事故复盘能回答
"谁在什么时候提议删了什么、谁确认的、执行了没有"。

**结论**：`interrupt()` 解决的是"怎么挂起"，而不可逆写真正的难点是
"确认能不能被伪造 + 状态能不能跨进程"。前者不需要框架，后者框架给不了。

### 10.2 其余配套决定

- **不装 `langchain-openai`**。模型调用仍走 `llm.chat()`（超时/降级/脱敏/用量统计都在那儿），
  适配器 `agent/model.py` 只有 40 行。装 SDK 会把 `llm.py` 里"不引 SDK"那条决定推翻一次。

| 文件 | 作用 |

四道独立的闸门（任何一道失效都算事故）：

1. **开关关着 → 模型看不见**（`action_enabled()` 过滤 `tool_schemas()`）；
2. **开关关着 → 校验不放行**（`validate()` 直接拒）；
3. **没有 `confirmed=True` → 不许执行**；
   这个参数**只有 `pending.confirm()` 会传**，所以老的"模型选工具 → 直接执行"路径
   （`_run_action()`）在结构上绕不过二次确认；
4. **执行必须落审计**（`feedback.delete`）并清掉图片文件。

第 3 条是这一批最重要的改动：它把安全属性写进了**最底层**，而不是靠"调用方记得先确认"。
