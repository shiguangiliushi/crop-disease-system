

## 一百三十一、第 142 批：被停用的账号登录时，终于说对了原因（且不再白白消耗失败次数）

**起点**：第 137 批做"停用/恢复"时实测到一个别扭现象 —— 把账号停用后，本人用**正确密码**
登录，看到的却是「密码错误，还可尝试 4 次」，而且**每试一次都在扣失败次数**，5 次之后
账号还会被临时锁定。用户手里拿着正确密码，却越试越像是自己记错了。

### 一、根因：那段代码在，但**够不着**

登录视图里本来就有这段（第 101 批写的）：

```python
if not user.is_active:
    if user.has_pending_deletion:  # 冷静期：给"取消注销"的自助入口
        ...
    return Response({'code': 'account_disabled', 'message': '账户已被禁用，请联系管理员'}, 403)
```

但 Django 的 `ModelBackend` 对 `is_active=False` 的用户**直接返回 None**
（`user_can_authenticate` 检查），所以 `authenticate()` 之后的这段**永远走不到** ——
被停用的账号落在前面"密码错误"的分支里。

第 101 批其实**已经发现过这个坑的一半**（冷静期账号也登不上、也拿不到引导），
当时的修法是在 `authenticate()` **之前**提前判 + 用 `check_password()` 自己验密码
（验过了才告知，避免"知道用户名就能探测该账号状态"）。但那个提前判的条件写的是
`existing_user.has_pending_deletion` —— 只盖住了冷静期，没盖住**管理员停用**。

### 二、修法：把提前判的条件放宽，两种"不可用"分别给说法

- 抽出 `_inactive_login_response(user)`：冷静期 → 带 `can_cancel`/`days_left` 的自助引导；
  被停用 → `code='account_disabled'`、文案「账户已被停用，请联系管理员」；
- 提前判的条件从 `has_pending_deletion` **放宽到 `not is_active`**，两半共用一份文案；
- `authenticate()` 之后那段改成调用同一个函数（留作兜底：万一将来认证后端换成
  "允许停用用户通过认证"的实现，这道判断还能接住）；
- 前端 `useLoginForm` 对 `account_disabled` **用语言包文案覆盖**后端那句中文
  （固定提示适合双语；带动态数字的"还可尝试 N 次"继续用后端文案）。

**防枚举仍然成立**：只有**密码正确**的人才能拿到"账号被停用"这个区别；
密码错的照旧只说"密码错误"并照常计数。已停用的账号不会因为"登录被拒"被锁定。
